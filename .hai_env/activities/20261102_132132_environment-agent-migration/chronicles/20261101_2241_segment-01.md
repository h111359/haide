## Outcome:
**Merging them is feasible, but I would keep them separate under the current design.** Activity-manager handles much more than records: it also performs assigned analysis, planning, implementation, and verification.

I’m assuming you mean one agent replacing these two, while Leader remains.

The main disadvantages are:

1. **A larger, less focused responsibility.** Environment-manager handles configuration, profiles, installation, and registration. Adding work execution, lifecycle management, and transcripts gives it substantially more instructions and exceptions to apply correctly. Separate procedure files would reduce this problem, but wouldn’t remove the broader scope. See their [Activity responsibilities](/home/hromar/Desktop/repos/haide/.hai/agents/activity-manager/SKILL.md:15) and [environment responsibilities](/home/hromar/Desktop/repos/haide/.hai/agents/environment-manager/SKILL.md:14).

2. **A model-selection compromise.** Activity-manager currently uses `advanced/high`; Environment-manager uses `light/high`. One agent declaration supports one default pair. You would either give routine administration the advanced model or give substantive Activity work the light model. Per-procedure selection could solve this, but requires changing the current [model-resolution design](/home/hromar/Desktop/repos/haide/.hai/conventions/model-profiles_conv.md:58). Actual cost and quality differences were not measured.

3. **Less explicit separation between settings and affected records.** Currently, changing an Activity location does not authorize moving records, and enabling chronicles does not authorize importing earlier exchanges. Separate owners make those boundaries visible. A merged agent would need equally explicit operation boundaries to avoid expanding a configuration request into unintended history changes. See [configuration handling](/home/hromar/Desktop/repos/haide/.hai/agents/environment-manager/procedures/configure-features.md:32).

4. **More complicated startup and failure handling.** Environment-manager must work before valid environment state or an Activity exists. Ordinary Activity work requires validated context. Combining them risks either circular prerequisites or accidentally extending startup exceptions to untracked substantive work. These are avoidable risks, but the [bootstrap boundaries](/home/hromar/Desktop/repos/haide/.hai/conventions/model-profiles_conv.md:89) must remain distinct.

5. **A coordinated migration across the framework.** Leader, shared conventions, and other agents reference Activity-manager and its procedures directly. Removing its folder requires updating routing, ownership statements, links, and verification coverage—not merely moving its instructions. For example, [Leader’s discovery procedure](/home/hromar/Desktop/repos/haide/.hai/agents/leader/procedures/coordinate-activity.md:32) explicitly delegates to it.

There are real benefits: fewer agent identities and fewer handoffs. Also, merging **does not inherently eliminate parallel execution**, and the current separation is an instruction boundary, not a security sandbox.

My recommendation: merge only if simplifying agent selection is your priority, while retaining distinct administration, Activity, and recording procedures with separate prerequisites and permissions. Otherwise, the present split is useful—particularly because the roles have different model requirements.

It should not independently declare product success merely because its records are internally consistent. The existing [recording-verification procedure](/home/hromar/Desktop/repos/haide/.hai/agents/activity-manager/procedures/verify-recording.md:41) illustrates that separate obligation.

With your proposed split, **I would support merging the remaining duties**, provided administration, Activity lifecycle, and recording retain separate procedures and permission boundaries. A separate Activity-manager would then be an optional organizational choice, rather than an architectural necessity.

**Chronicle-manager has the clearest independent responsibility.** Exact source identity and transcript coverage differ substantially from ordinary work summaries and environment configuration. Activity-manager already has separate [recording procedures](/home/hromar/Desktop/repos/haide/.hai/agents/activity-manager/SKILL.md:124).

Its boundaries should remain explicit:

- Environment-manager controls recording settings.
- Leader assigns Activities and source ranges and schedules recording.
- Chronicle-manager writes and verifies transcripts.
- The Activity record owner handles lifecycle and closure.

The main added cost is closure coordination: closure currently verifies recording within the same agent. Splitting it requires Leader to obtain fresh coverage evidence before authorizing the record owner to finish closure.

**Agent-package-manager is another coherent extraction.** Installation and registration share package identity, validation, replacement, and catalogue concerns. I would keep them together initially. Definition authoring would remain with Agent-definition-manager. The existing [installation workflow](/home/hromar/Desktop/repos/haide/.hai/agents/environment-manager/procedures/install-source-package.md:31) already connects these duties.

This agent must be available during bootstrap; installing the first optional agent must not require an installer that is itself missing.

**Model-profile-manager is possible, but less compelling.** It becomes worthwhile with multiple runtimes or frequent mapping changes. It should not select specialists, schedule work, or take ownership of other agents’ settings. Those are different responsibilities.

I would **keep these groups together**:

- Environment validation, initialization, core configuration, and core migration: they share state contracts and preservation requirements.
- Activity identity, discovery, revisions, supplements, and closure: they form one lifecycle.
- Package installation and registration: separating them adds coordination around tightly related changes.

For your proposed design, I would start with **Environment-manager owning core setup and Activity records, plus a separate Chronicle-manager**. Add Agent-package-manager only when its workload warrants it. That creates useful boundaries without turning every procedure into an agent.
