# Documentation contract and completeness gate

`documentation/tree.yaml` uses `schemas.json#documentation_tree`. Every node has a stable canonical ID, title, scope summary, applicability/status, when-to-read guidance and exactly one parent except root. Internal catalog nodes contain navigation only. Actual documentation lives in terminal content leaves. Child IDs are structural; cross-links are not. Resolve topic IDs through the tree.

Defaults: at most eight children per catalog; deepest minus shallowest leaf depth at most one; target at most 1,500 words per leaf. Configure these limits without changing the schema. No cycles, missing paths, unreachable leaves, multiple parents or duplicate IDs. Every path must stay inside current documentation. Exceptions for indivisible reference material include a reason. Balance by meaningful grouping without empty padding. A split retains the continuing topic's ID and records new IDs and old-reference mappings. Commit multi-file changes recoverably with revision checks; supported readers lock or retry a changed snapshot.

Each leaf records provenance, update date, source references and hashes bound to root identity/workspace revision, owning request or system operation, decisions, verification status, unresolved review items and preserved human-authored sections. Distinguish extracted facts, inferred requirements, approved intent, observed implementation, verified behavior and deployment. A static inventory never proves runtime behavior. Reuse evidence only while source/instruction/extractor/schema/core and relevant workspace dependencies remain valid.

`coverage.json` enumerates all required categories. The applicability catalog assigns every category one of `applicable`, `not-applicable` with evidence-backed rationale, or `unknown` with an investigation limitation. Applicable local coverage requires substantive topic evidence, not an empty heading. External unknowns may remain explicit. Uninspected available local content is missing coverage and blocks the baseline. Every registered root, including read-only sources, must be represented in the inventory and relevant coverage.

Initial completeness checks require: inventory of authorized local content with omissions explained; all category dispositions; substantive applicable knowledge; current provenance; valid balanced tree and links; explicit unknowns/contradictions; and reconstruction review. The gate binds current workspace revision and manifest hash. Adding/relocating roots marks affected coverage unresolved. A baseline can be complete while product tests remain unrun; these states must stay separate.

Reconstruction review checks business rules, interfaces, expected results, dependencies, acceptance/test mappings and recovery prerequisites. Identify unsupported claims and gaps. Record `specified but not demonstrated` until an independent explicitly authorized reconstruction exercise supplies separate evidence. Ordinary test success and completeness review cannot demonstrate reconstructed equivalence.

Each request's documentation increment lists canonical topic/section, reason, requirements/decisions, owning task, planned change, status, before/after hashes/diff and verification. A justified no-impact determination is explicit. Planned changes are never current behavior. Successful completion requires reconciliation with actual results. Partial implementation causes visible drift. Cancelled/rejected closure leaves a discoverable current-state notice with retained changes, affected IDs, defects, uncertainty and archived evidence; it does not queue work.

Known defects retain ID, symptoms, reproduction/evidence, components, impact, supported workaround, disposition, origin and verification of resolution. Suspected defects remain unconfirmed. Clarify may perform only evidence-backed defect/staleness bookkeeping; substantive documentation changes need documentation authority. Independent Q&A cannot modify durable product documentation.
