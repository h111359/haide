# Architecture exploration analysis

## Scope and accepted constraints

The user requested exploration of an agent runtime in `.hai` that contains no agents and has permanent concepts, conventions, procedures, and templates. Configuration belongs in `.hai_env`, and the runtime should be universally applicable across agents. The accepted scope is exploration and design only. No implementation or runtime/configuration/agent edits are authorized.

## Specialist evidence

Registered `agent-definition-manager` (`gpt-6.1-sol`, high reasoning) completed a focused read-only architecture review. The review identified these current structural couplings:

- `.hai/start.md` hardcodes Leader as the startup entry point.
- `agent_conv.md` reserves built-in roles and named delegation relationships.
- `procedure_conv.md` requires procedures to be owned by individual agents.
- `state_conv.md` places the shared schema and template within Environment-manager.

No implementation, repairs, or product tests were performed by the specialist.

## Proposed direction (not an approved design decision)

The specialist proposed making `.hai` a versioned, role- and provider-neutral protocol package containing permanent concepts, conventions, shared procedures, schemas, templates, and tools. All agent definitions and selected configuration would live under `.hai_env`. A generic bootstrap would run inside an already-running host and load an environment-selected entry agent. Runtime procedures would describe inputs, results, and required capabilities without naming roles. Schemas would define contracts; templates would remain inert setup inputs, with active defaults materialized in the environment.

In this proposal, “universal” means usable by conforming agents that declare their host capability requirements. It does not promise that every host provides every capability. This proposal is recorded as specialist analysis, not as a user-approved decision.

## Unresolved design choices

1. Should the runtime be an instruction protocol with optional tools, or an executable engine with a mandatory host API?
2. Should Activities remain mandatory, or become a configurable capability?

Runtime policies remain unchanged during this exploration unless the user later approves a design and implementation scope.
