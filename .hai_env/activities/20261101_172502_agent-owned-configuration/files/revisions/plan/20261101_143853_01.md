# Plan: agent-owned configuration as a standard HAI characteristic

Status: proposed implementation plan; no framework, agent, configuration or runtime migration changes have been made. Activity: `963b571a-13e1-4b39-a3aa-d2938d388b67`, `.hai_env/activities/00000000_000000_active`.

## Objective and decisions

Make configuration ownership a required characteristic of every current and future agent. Agent-definition-manager must enforce the characteristic during creation, update, validation, registration and installation. Preserve a small central environment contract, existing settings, user permissions, work records, optional-package independence and source/installed-package boundaries.

The user has settled the direction and requested a comprehensive plan. The following are proposed design choices for that plan, not existing policy:

- Every agent declares a configuration contract, including agents that have no customizable settings. Physical workspace configuration files are required only when saved settings are needed. This interprets “all agents” as universal ownership/contract coverage; it does not introduce meaningless empty override files.
- Mutable configuration lives at `.hai_env/config/agents/<agent-name>.json`, outside reusable and installed agent packages. Names are already unique across both runtime origins.
- Retain `.hai_env/state.json` for environment-format compatibility and the mandatory shared `activities.location`. Fixed instructions, catalogues and model profiles retain their separate locations and ownership.
- First establish the standard and extract Git-manager's extension settings, preserving existing shared feature configuration. As a subsequent, explicit extension of the earlier recommendation, the recommended final target also extracts specification settings to Specification-manager and chronicles settings to Activity-manager. This ownership change must be accepted as part of implementation scope; it is not a previously settled decision.
- Configuration format versions are independent of core state versions, product/specification compatibility versions, package identity and release SemVer. New configuration versions do not create an automatic updater or agent-version scheme.

## Implementation sequence

### 1. Establish the shared contracts and authoritative mapping

Owner: Agent-definition-manager for framework conventions, concepts and definitions; Leader coordinates review with the configuration owners.

Add `.hai/concepts/agent-configuration.md` to explain ownership, reusable defaults versus workspace values, configuration versus progress, dependency isolation and upgrade boundaries. Add `.hai/conventions/agent-configuration_conv.md` as the single shared representation and validation contract. Update `agent_conv.md`, `state_conv.md`, `framework-layout_conv.md` and `model-profiles_conv.md`; revise `concepts/agent.md`, `concepts/environment.md` and relevant `concepts/hai.md` descriptions. Preserve the six required SKILL sections and existing procedure structure.

Proposed machine-readable declaration: a required quoted string metadata key `hai-configuration-contract: "configuration/contract.json"`, resolving within the agent's installed package. Every agent has that file, including an explicit no-settings contract. Use a separate path because Environment-manager's existing root `contract.json` governs state format and Specification-manager's governs tree compatibility. Do not overload either.

Define a small, documented data-only configuration-contract format: agent identity, contract-format version, current/supported configuration-format versions, settings declarations/types/defaults, missing-file behavior, allowed unknown-value behavior, relevant paths and dependency declarations. Define enough schema vocabulary for actual settings and implement it with the existing Python standard-library approach; unsupported declarations must be reported rather than guessed. Do not add executable validators or arbitrary imports to configuration data. Keep contract defaults authoritative in one place; examples/templates must be checked against them rather than become competing defaults.

Workspace files use a strict JSON envelope with `config_format_version` and `settings`. Reject duplicate keys, invalid numeric constants, wrong types and Boolean-as-integer versions/thresholds. Missing files use explicitly declared defaults; invalid/unreadable/unsupported files do not fall back silently. Required settings without defaults are dependencies. Preserve unknown values during authorized writes, but never activate behavior from them. No-settings contracts reject attempted active settings instead of silently adopting them. Report saved, defaulted, invalid, incompatible and unverified conditions with provenance. Preserve Git's distinction between missing/unconfigured and explicitly disabled where its public result contract requires it.

Only the owner changes its settings under task authority. Configuration is not registration, capability readiness or permission. Do not store credentials, tokens or live readiness evidence. Central profiles remain the authority for concrete model mappings; agent configuration cannot bypass model resolution or rewrite SKILL rules.

Reserve `.hai_env/config/` against Activity/specification roots and aliases to instructions, state, profiles, registries, framework or Git resources. Validate lexical and resolved paths, existing ancestors, symlinks/junctions, file types and cross-file aliases before reads and writes, including disabled settings. Config files must not alias one another. Initialization must preserve existing configuration and not manufacture optional records or defaults files.

Acceptance: a complete old-to-new ownership table, one authoritative schema/default source per setting, universal contract requirement and explicit no-settings behavior; no conflict with fixed instruction loading, registration or bootstrap rules.

### 2. Implement common read-only validation before changing runtime writers

Owners: Environment-manager owns startup policy and common configuration-loading behavior; Agent-definition-manager owns definition-format enforcement. Supporting implementation follows each owner's authorized procedures and the tooling convention.

Add a documented shared configuration helper under `.hai/tools/configuration/` with a read-only CLI, tests and reusable strict data/path utilities. Avoid circular imports: configuration parsing cannot depend on startup running or an agent invocation; factor shared containment/JSON primitives if needed while retaining compatibility for Git-manager's existing imports.

Update `.hai/tools/agents/agent_tools.py`, its README and fixtures/tests. `validate --definition` must verify required metadata, package-contained contract, identity, supported contract/schema versions, defaults, path policy, dependency declaration structure and explicit no-settings declarations without requiring state, profiles, registration or a workspace override file. Full audit covers all registered definitions and can report saved configuration separately. Preserve standalone format inspection for unregistered installed targets and source staging in canonical runtime layouts.

Update `.hai/tools/startup/startup_check.py`, its README and tests. Core validation and agent-configuration results must have independent status scopes. Keep instructions first, valid catalogue-based selection, no recursive source discovery, no Activity enumeration, no optional content loading and no automatic writes. Routine startup need not parse every SKILL or load every optional configuration. It can read fixed core configuration contracts and explicitly requested registered-owner contracts using the shared data reader. Selected-agent validation verifies metadata linkage before invocation. Never execute package scripts merely to load settings.

Acceptance: absent configuration files and no optional agents allow fresh core startup; one malformed optional configuration does not invalidate core state or unrelated roles; readers never write; configuration validation does not require its owner to have already been invoked.

### 3. Make Agent-definition-manager enforce the characteristic

Owner: Agent-definition-manager; change its golden package first.

Update `SKILL.md`, `concepts/definition-management.md` and all applicable procedure files in `hai_agents_library/agents/agent-definition-manager/`.

- Establish-scope inspection inventories the target contract, workspace config, schema/default compatibility, ownership/dependencies and source/installed baseline.
- Creation requires a meaningful configuration declaration and generates the contract even when settings are explicitly empty. It never invents user settings or activates capabilities.
- Update reviews configuration-contract compatibility and required migrations, preserves values and registration, and does not silently turn a definition update into a settings migration.
- Validation/audit enforces declaration, defaults, references, safe paths, dependency boundaries, absence/error behavior and no-settings semantics.
- Registration requires valid definition/contract evidence; a missing override file with declared defaults does not block registration. Runtime configuration failures are reported separately from definition eligibility.
- Installation/update copies contracts/default resources with the complete package, stages against compatible core and peers, preserves all `.hai_env/config/` values, checks existing saved-config compatibility and reports required migration. No source fallback, implicit enablement or automatic config conversion.

Add the same contract requirement to reusable creation examples/templates in `agent_conv.md` and any affected installation documentation. Contract changes must be reviewed semantically, not merely checked for a metadata key.

Acceptance: a newly authored agent cannot pass validation/register without its declaration; a no-settings agent passes without a workspace JSON file; replacing a package does not overwrite configuration.

Acceptance: Git validation reads its file and is insulated from unrelated core JSON contents; operations still require valid core context. Current true/true/false settings survive exactly. No Git/GitHub operation or network readiness probe is needed merely to move unchanged saved settings.
