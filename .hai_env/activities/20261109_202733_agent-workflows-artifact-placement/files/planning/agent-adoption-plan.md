## Design proposed for implementation

1. **One plan is the execution brief.** Extend the existing architect plan convention and use the Activity's `plan.md`. Keep exploratory reasoning in `analysis.md`; the developer cannot infer additional scope from it.
2. **Reuse existing authorities.** Business analyst owns business readiness, clarification dialogue, contextual registry reading and framework-protection contracts. Core owns Activity records, chronicles, history and lifecycle; Specification-manager owns managed specification updates.
3. **Declare peer dependencies.** Resolve required peer contracts from installed sibling packages. Missing required peers block only dependent work; do not load reusable library packages as executable roles or silently copy peer contracts.
4. **Keep modes explicit.** Architect supports normal assessment/planning and explicitly selected accelerated planning. Developer supports plan-based execution and an explicitly authorized substantive direct directive; no magic command phrase is required.
5. **Preserve safeguards in every mode.** Accelerated/direct work cannot bypass mandatory readiness, authorization, conventions, ownership or workspace boundaries. Disclose choices actually delegated by the caller.
6. **Use proportionate verification.** Require appropriate coverage for acceptance criteria, with explicit justification for inspection-only checks or absent documentation work. Do not require redundant tests for low-impact reversible edits.
7. **Keep new helpers pure.** Standard-library validators inspect explicitly supplied current documents/evidence and emit diagnostics. They do not repair documents, write records, allocate identities, discover unrelated sessions or claim semantic acceptance.

These proposals deliberately adapt literal source requirements: preserve delegated technical discretion; log material issues encountered without an exhaustive audit; retain HAI's no-automatic-retry rule for partial persistence failures and permitted archive supplements; prefer staged knowledge replacement over destructive deletion.

The general workspace boundary already exists in core. Both agents reference it; do not restore the removed duplicate workspace-local instruction or create alternative package-local boundary policies.

## Contract implementation details

### Assessment and technical readiness

Require ordered unique sections for identity/input provenance, interpretation, scope/exclusions, evidence and findings, edge conditions, options, knowledge effects, decisions and readiness. Preserve exact user input through current records rather than substituting an interpretation.

Assess technical readiness with stable check IDs: current requirements evidence; known affected components; resolved critical decisions; compatibility/failure behavior; feasible verification; explicit owner/permission dependencies. Failed checks identify the affected action and corrective dependency.

Research attachments fully within authorized scope; identify nested supplied materials and unreadable/nontext limits. Record material out-of-scope concerns individually and return them without repairing them.

### Plan and decision freshness

Preserve the existing phase overview and seven-part phase layout. Add an opening contract identifying Activity, current input/decision evidence, mode, scope, authority, constraints, accepted assumptions, acceptance criteria and required owners.

Use unique task/acceptance IDs, exact destination paths and an explicit task-to-acceptance mapping. Specified executable operations include invocation, expected result and output location; unresolved locations remain dependencies instead of invented targets.

Record business, technical, timing and authorization limits or explicitly state no additional supplied limit. Include documentation/knowledge work and validation, or a reason why none is required.

Technical decisions record alternatives, effects, recommendation, actual outcome and source. Only decisions already delegated or determined by applicable authority can be resolved without asking; recommendations and interface preselection never count as answers.

The host verifies source revisions/hashes and actual decisions before persistence and before execution. A structural validator can check the supplied evidence shape; it cannot authenticate user permission or the truth of a readiness claim.

### Execution evidence and helpers

Execution evidence records the directive used, mode, current input checks, task results, own changed paths against baseline, check status, documentation/owner results, deviations, protection inspection and remaining dependencies. Missing mandatory evidence blocks verified success.

Both CLIs are read-only: explicit `--workspace`, explicit document/evidence inputs, UTF-8 JSON output, exit 0 for structurally valid input, 1 for validation findings and 2 for unreadable/unsafe/invocation failure. Publish exact arguments with F10/F20 before use.

Validate documented Markdown structure, duplicate headings/IDs, required fields, task dependencies, target declarations and acceptance references. Required semantic checks stay with the executor/reviewer; reject unsupported syntax with diagnostics rather than silently rewriting it.

Reuse architect's plan parser in developer plan mode through a validated installed peer path. Direct mode validates its own substantive directive contract; missing architect tooling blocks plan validation, not independent direct-input diagnosis.

Preserve immutable input evidence supplied to the helper; no validator allocates Activity/question identities, advances state, authenticates approvals, installs dependencies or writes a repaired document. Suppress bytecode and keep any caller-managed outputs within the workspace.
