There are two different kinds of state here: **configuration** (“record every five prompts”) and **recording progress** (“which messages have actually been saved”). I would keep their responsibilities separate:

| Agent | Responsibility |
|---|---|
| Environment-manager | Maintain and validate the enablement setting and prompt threshold. |
| Leader | Use those settings, count incoming prompts, and initiate recording when due. |
| Chronicles-manager | Save transcripts and maintain verified recording progress, including pending messages and gaps. |
| Activity-manager | Maintain Activity identity and lifecycle; prevent closure until required recording is verified. |

One correction to your understanding: Environment-manager owns the **global** `.hai_env/state.json`. Activity-manager owns the **individual Activity’s** records and state. They do not both need to watch the global configuration.

The ordinary flow would be:

1. At startup, Leader receives the validated settings through the existing startup helper.
2. Leader counts actual user prompts assigned to the current Activity. Tool calls and agent messages do not count.
3. At the fifth prompt, Leader starts a recording batch and continues working on your request.
4. Chronicles-manager returns the saved message boundaries and any remaining gaps.
5. Leader avoids starting another batch while one is already running.

Counting incoming prompts is coordination bookkeeping. It does not require Leader to edit environment configuration or Activity records.

**I would avoid writing the changing counter into global `state.json` after every prompt.** Leader can maintain it during the conversation and reconstruct it after a restart from saved user-message identities and Chronicles-manager’s progress record. If we require an on-disk counter updated on every prompt, we would need a small tool with explicitly assigned write responsibility. Calling a manager agent just to increment a number would recreate the overhead we want to remove.

An important detail: when prompt five arrives, its answer does not yet exist. That batch records the available saved conversation; the fifth answer remains pending for a later batch.

Regarding parallel agents: **an agent session is a separate AI conversation and execution task managed by the runtime. It is not necessarily a separate operating-system process.** Each agent has its own context and can perform work concurrently. [Official OpenAI multi-agent documentation](https://developers.openai.com/api/docs/guides/responses-multi-agent)

In this interface, communication works through explicit tools:

- `spawn_agent`: creates an agent and supplies its assignment.
- `followup_task`: gives an existing agent more work.
- `send_message`: sends information to an existing agent; it does not start an idle agent.
- Results arrive as messages to Leader.

Agents also share the workspace files. They **do not automatically receive every later message in the main conversation**. Leader must supply relevant updates, such as a changed Activity. Background recording here means concurrent work during active execution; continuation after Leader’s final reply depends on runtime support.

Finally, **closure bypasses the five-prompt threshold**: when chronicles are enabled, Activity-manager requires fresh recording verification before closing. Missing required coverage keeps the Activity open. If the conversation simply stops after four prompts, those messages remain pending until the next trigger or closure request.
