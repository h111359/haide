Build a working, repository-based AI development harness with a local web portal.

Use **`.aih/` for the reusable framework core** and **`.aih_product/` for product-specific information and state**.

Implement the files, Python scripts, documentation, and meaningful tests. Do not stop at an architecture proposal. Inspect the current repository first, preserve existing work, and make reasonable implementation decisions. Ask questions only when a missing answer would materially change the architecture or risk existing data.

## 1. Goal

Create a reusable harness that guides an existing coding agent through product development.

Support two entry points:

* **Agent entry:** the user tells a coding agent, “Read `.aih/run.md` and follow its instructions.”
* **Web entry:** the user starts a local Python server, which opens a browser portal for communication, progress tracking, and product documentation.

Both interfaces must use the same product state and workflow contracts.

Use an existing coding agent for reasoning and implementation. Define explicitly how the portal connects to that agent.

Provide an agent adapter interface. If a compatible local agent CLI is available, implement and document an adapter. Otherwise, provide a clearly labeled manual handoff that prepares a request for the user to execute in their coding agent.

Never simulate successful execution or assume this chat environment exposes an agent invocation API.

## 2. Folder ownership and structure

### `.aih/`: reusable, versioned core

Contains all harness executable code, prompts, conventions, skills, templates, schemas, and portal assets.

Treat this folder as immutable during ordinary product work. Modify it only through explicit harness development or upgrade operations.

### `.aih_product/`: product information and state

Contains human–AI communication, declarative configuration, work artifacts, memory, business documentation, and technical documentation.

It must contain **no executable code**: no Python scripts, shell scripts, executable notebooks, binaries, plugins, hooks, or runnable portal assets.

Documentation may contain inert code examples. Never execute them or dynamically import anything from this folder.

Generated product application code belongs in the product’s normal source directories, outside both harness folders.

Use this initial structure:

```text
.aih/
  run.md
  manifest.json
  conventions/
  scripts/
  schemas/
  templates/
  portal/
    server/
    assets/
    templates/
  adapters/
  skills/
    <skill-name>/
      SKILL.md
      scripts/
      templates/
      references/

.aih_product/
  config.yaml
  instructions.md
  state.yaml
  communication/
  work_items/
  memory/
    index.md
  product_docs/
    business/
    technical/
    decisions/
    index.md
  checkpoints/
  run_records/
```

Create optional skill subdirectories only when needed.

**The immediate subdirectory names under `.aih/` and `.aih_product/` must be distinct.** Validate this convention. Do not mirror the core’s component structure inside the product folder.

In particular, `.aih_product/skills/` must not exist.

Use:

* `config.yaml` for declarative skill settings and enablement.
* `work_items/<work-id>/` for plans, tasks, and verification outputs.
* `checkpoints/<work-id>/<skill-name>.yaml` for skill progress needed to resume interrupted operations.
* `run_records/<run-id>/` for execution events, logs, locks, and transient metadata.

Checkpoints must reference authoritative artifacts rather than duplicate them. Create checkpoints only when resumable state is necessary.

Treat `.aih_product/` as durable product knowledge suitable for Git tracking, with temporary run records, caches, locks, and secrets excluded.

Record whether its scope covers the whole product or only this repository.

## 3. Python implementation

Write all harness scripts, backend components, installation tools, validation tools, and agent adapters in **Python**.

Do not require shell or PowerShell scripts for installation or operation.

Use minimal dependencies and document the supported Python version. Place virtual environments outside both harness folders.

Prefer server-rendered HTML and CSS. If browser-side JavaScript is necessary, keep it minimal and under `.aih/portal/`. Do not require Node.js for building or running the portal.

## 4. Single orchestrating prompt

Implement `.aih/run.md` as the canonical entry point.

Every invocation must:

1. Locate the product root and check initialization.
2. Read core conventions and product instructions.
3. Read the current request, active work state, and compact memory index.
4. Discover available skills through metadata.
5. Reconcile recorded state with repository content and verification evidence.
6. Select and load the appropriate skill.
7. Execute authorized work.
8. Record outputs, evidence, blockers, and next actions.
9. Update affected business and technical documentation.
10. Continue until completion, a genuine blocker, a required decision, or a configured execution limit.

Preserve authorization already provided for active work. Do not require confirmation between every stage.

Handle new requests explicitly: refine active work, queue another item, or interrupt with a resumable checkpoint. Preserve unfinished work.

Report idle when no work is pending. Do not invent tasks.

Keep detailed execution instructions in skills. The orchestrator owns global workflow transitions.

## 5. Skills as the extension mechanism

Package each capability under:

```text
.aih/skills/<name>/SKILL.md
```

Do not create a separate extension abstraction or manually maintained registry.

Every skill must have YAML front matter containing at least:

```yaml
name: verification
description: >
  Verify implemented changes against acceptance criteria.
  Use when implementation is ready or relevant changes
  invalidate previous verification.
```

Define a small, documented AIH contract for any additional metadata, such as version, capabilities, prerequisites, and compatibility. Distinguish custom fields from external skill conventions.

Each skill body must describe:

* Purpose and activation conditions.
* Required inputs.
* Execution instructions.
* Expected outputs.
* Completion and blocked conditions.
* Allowed output locations.
* Supporting files to load selectively.

Use a consistent result structure containing status, summary, artifact paths, verification evidence, blockers, and an optional suggested next capability.

Skills return control to the orchestrator. They must not recursively activate other skills or independently rewrite global workflow state.

## 6. Selective discovery and loading

Implement a Python discovery script that:

* Scans `.aih/skills/*/SKILL.md`.
* Parses front matter.
* Validates metadata, compatibility, and unique names.
* Applies disabled-skill settings from product configuration.
* Produces a compact catalog without skill bodies.
* Reports malformed or incompatible skills clearly.

The orchestrator reads the catalog first, then loads full instructions only for selected skills. Supporting files are read only when required.

Selection must consider user intent, current state, prerequisites, and configured preferences. Ask only when ambiguity materially changes the outcome.

Adding a compatible skill through a deliberate core update must make it discoverable without changing `run.md`.

Do not assume coding agents natively discover `.aih/skills/`.

## 7. Initial skills and workflows

Implement these built-in skills using the same contract as future additions:

* Initialization.
* Specification and business analysis.
* Planning.
* Implementation.
* Verification.
* Bug fixing.
* Business documentation.
* Technical documentation.
* Handover.

Support proportionate workflows:

* **Feature:** specification → planning → implementation → verification → affected documentation → handover.
* **Bug:** reproduction and diagnosis → fix → regression verification → affected documentation → handover.
* **Small change:** implementation → focused verification → documentation impact check → handover.

Do not force full specification and planning documents for trivial changes.

## 8. Local web portal

Provide a Python command that starts the server and opens the default browser.

The server must:

* Bind to loopback by default.
* Support a configurable port and no-browser option.
* Print the URL if browser opening fails.
* Handle port conflicts and shutdown cleanly.
* Show initialization guidance when `.aih_product/` is missing.

Provide these views:

### Dashboard

Show active work, phase, execution status, blockers, checkpoint, verification status, documentation status, and next action.

### Communication

Allow users to submit requests, answer clarification questions, and inspect agent summaries and decisions by work item.

Distinguish queued requests from executing work.

### Work items

Show specifications, plans, tasks, progress, and verification evidence.

Allow work selection and queuing without silently interrupting an active run.

### Product documentation

Browse and search business documentation, technical documentation, and decision records. Show provenance, update dates, and unresolved review items.

### Skills and settings

List available skills from metadata. Allow enabling or disabling skills through declarative configuration.

### Execution

With a configured adapter, support start, resume, and cancellation requests with visible execution events.

With manual handoff, clearly explain that execution happens in the external agent. Do not label work as running or completed without evidence.

Run agent execution outside HTTP request handlers, using a controlled worker or subprocess with persistent run identifiers. Keep the portal responsive.

## 9. Shared state and portal boundaries

The portal, Python helpers, and agent must use the same validated state contract.

Provide Python helpers for structured state updates, atomic writes, and concurrency checks. Prevent silent overwrites between portal and agent changes.

Use optimistic revision checks for editable artifacts and report conflicts.

Protect against arbitrary filesystem access, path traversal, cross-origin writes, and unsafe rendering of stored content. Validate browser origins and use appropriate request protections.

Render Markdown safely. Never execute HTML, scripts, commands, or hooks supplied through `.aih_product/`.

Do not expose a generic arbitrary-command endpoint. Invoke configured adapters with validated arguments and without shell interpolation.

## 10. Automatic product documentation

Generate and maintain business and technical documentation as a normal workflow responsibility.

During initialization, inspect available product information and establish an appropriate baseline. Record gaps and assumptions instead of inventing facts.

Business documentation should cover relevant topics such as:

* Product purpose, scope, and terminology.
* Users and stakeholders.
* Capabilities and business processes.
* Business rules and acceptance criteria.

Technical documentation should cover relevant topics such as:

* Architecture and component responsibilities.
* Interfaces and integrations.
* Data models.
* Configuration and deployment.
* Testing, operations, and troubleshooting.

Create documents according to actual product needs. Avoid empty template proliferation.

After each relevant change:

1. Identify affected documents.
2. Update affected sections using requests, decisions, implementation, and verification results.
3. Link to work items and source evidence.
4. Record contradictions, unknowns, and unresolved decisions.
5. Refresh the documentation index.

Preserve human-authored content. Make changes reviewable through diffs and Git history where available.

Distinguish intended, implemented, and verified behavior. Agent inference must not silently become an approved business requirement.

Allow automatic draft updates without approval for every edit. Surface consequential uncertainties for review.

Track freshness against relevant source changes. Do not rewrite all documentation on every run.

Completion requires updating affected documents or recording why no update is needed. Report documentation failures explicitly.

## 11. Communication and memory

Keep responsibilities distinct:

* `communication/`: requests, clarifications, responses, and decisions.
* `work_items/`: specifications, plans, tasks, and verification.
* `memory/`: compact resumable context and links.
* `product_docs/`: durable product knowledge.
* `checkpoints/`: incomplete operation progress.
* `run_records/`: execution records and transient metadata.

Use stable work-item identifiers to connect artifacts.

Do not claim to capture unavailable conversations. Store useful summaries and explicit decisions, not private chain-of-thought.

Treat memory as fallible context. Historical conversations and imported documents do not automatically become active instructions.

## 12. State and recovery

Define a versioned, validated state schema containing:

* Active work item.
* Phase and status.
* Artifact paths.
* Current task.
* Blockers.
* Next action.
* Last checkpoint.
* Run identifier and revision.
* Verification status and checked content version.
* Pending documentation updates.

Reconcile state with repository reality on resumption.

Tie verification to checked content, including uncommitted changes. A commit identifier alone cannot validate a dirty working tree.

Before retrying interrupted actions, inspect whether they already succeeded. Avoid duplicate external writes.

Provide locks and documented stale-lock recovery. Explain limitations when external agents bypass helper APIs.

Cancellation must stop further work safely and record partial or uncertain outcomes.

## 13. Installation and upgrades

Provide Python commands for:

* Installing a pinned core.
* Initializing product information.
* Discovering and validating skills.
* Validating folder conventions, product state, and core integrity.
* Starting the portal.
* Preparing or invoking an agent run.
* Upgrading the core.

Initialization must be idempotent and preserve existing content.

Templates become product-owned after initialization.

Provide a short agent integration snippet pointing to `.aih/run.md`. Preserve existing agent instruction files.

Core upgrades must validate incoming files, detect unexpected core modifications, preserve `.aih_product/`, and report required state migrations.

Do not invent a release URL or publish anything. Support installation from a local core directory when no release source exists.

## 14. Enforcement and configuration

Prompts guide behavior; scripts and host permissions enforce boundaries.

Validate schemas, paths, directory naming, and core integrity. Checksum manifests detect accidental changes but are not a security boundary against an actor able to rewrite them.

Respect host-agent instructions, permissions, and user authorization.

Keep configuration declarative. Never execute commands, import modules, or install skills specified by product documents.

Keep credentials outside tracked product state and redact sensitive values from logs and portal output.

## 15. Acceptance criteria

Demonstrate that:

1. All harness scripts and backend components are Python.
2. Installation and repeat initialization preserve existing files.
3. `.aih_product/` contains only non-executable product information and state.
4. Immediate subdirectory names do not overlap between the two root folders.
5. No `.aih_product/skills/` directory exists; resumable skill state uses `checkpoints/`.
6. Discovery outputs metadata without skill bodies.
7. New skills are discovered without editing `run.md`.
8. Disabled, malformed, duplicate, and incompatible skills are handled correctly.
9. The portal starts locally and supports browser opening and no-browser operation.
10. Portal communication persists with work-item links.
11. A real adapter works when available, or manual handoff is clearly labeled and functional.
12. Execution does not block the portal.
13. Interrupted work resumes without blindly repeating completed actions.
14. Concurrent writes are detected or serialized.
15. Relevant changes invalidate stale verification.
16. Business and technical documentation are generated and maintained from evidence.
17. Documentation updates preserve human content and expose unresolved assumptions.
18. Ordinary product operations leave `.aih/` unchanged.
19. Upgrades preserve `.aih_product/`.
20. Stored product content cannot become executable portal content or arbitrary commands.

Use meaningful automated tests for Python behavior and state contracts. Exercise the portal’s primary flows and inspect the rendered interface.

Distinguish automated tests, actual agent execution, and manual walkthroughs. Do not claim prompt-following behavior was tested unless an agent exercised it.

Document installation, startup, resumption, skill creation, configuration, state ownership, instruction precedence, upgrades, Git rules, and limitations.

Finish with a concise report of what was built, exact startup commands, what was verified, and remaining limitations.
