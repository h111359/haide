# Impact analysis: copy-installed HAI agent library

This is a read-only architectural review, not an implementation. No agent, registry, configuration, release metadata, or Git state was changed. No Git commands or tests were run. Evidence comes from bounded file inspection of the four packages, core selection/definition/startup tools and contracts, and current installation/release documentation. Prior analysis remains unchanged.

## Finding and proposed interpretation

The proposed `hai_agents_library` is a sound separation of reusable optional **source packages** from core runtime and workspace-installed **snapshots**. It should not become a third executable agent origin. Ordinary HAI execution should continue to recognize only `.hai/agents` and `.hai_env/agents`; copying a package and explicitly registering its installed definition makes it eligible. A library index describes installables, not registered workers.

Moving folders alone is insufficient. The important impacts are registration/bootstrap, definition-manager source-maintenance authority, relative references, specification ownership links, release distribution and contract snapshots, and future copy/update policy. These are concrete integration issues, not reasons to reject the approach.

The understood proposal is:

- Move Specification-manager and Agent-definition-manager source packages out of `.hai/agents` into the library.
- Copy existing Git-manager and Release-manager packages from `.hai_env/agents` into the library while retaining their installed copies.
- Install the intended optional managers into `.hai_env/agents` and register those installed copies. The duplicated manager name in the user's instruction still needs clarification: this report evaluates the likely Specification-manager plus Agent-definition-manager branch without treating it as settled.
- Preserve current Leader, Environment-manager and Activity-manager architecture. Their earlier proposed refactoring is outside this step.
- Never use library code/instructions as an ordinary runtime fallback for an absent or stale installed agent.

Two boundaries need explicit wording. Reading a library package to **install, compare, maintain, test or package source** is a source-management operation. Loading that package's rules/helpers/contracts as the authority for an installed agent's ordinary task is a runtime dependency and would violate the proposal. A provenance field may identify the original source revision without being followed automatically during execution. A literal ban on every library read by an agent would also prohibit authorized source maintenance and installation; that is probably broader than intended and should be confirmed.

## Portability of the four packages

**Specification-manager:** strongly reusable and already standalone-capable. The full package and helper can operate outside HAI; its HAI-managed work still requires compatible enabled specification context, configured root and Activity, and cannot be relabeled standalone to evade disabled/missing HAI context (`.hai/agents/specification-manager/SKILL.md:40–45`). Installing its snapshot must not enable specification, create a product tree, change the root, or migrate an existing tree. Compatibility version 1 describes specification data, not general agent/core compatibility.

**Agent-definition-manager:** reusable HAI administration tooling, not a fully independent package today. It depends on shared conventions, core helpers, registration and Activity policy. Moving it optional is feasible, but source-library maintenance, installation ownership and self-bootstrap need explicit additions. Core remains usable without it for ordinary startup and other installed work; definition design/registration operations become unavailable until it is installed. Leader currently routes role-placement proposals to this owner (`.hai/agents/leader/procedures/delegate-work.md:32`), so missing owner should produce a precise optional-package dependency, never silent Leader takeover.

**Git-manager:** reusable across compatible HAI workspaces, not specific to this repository's remotes/branches. It explicitly discovers identity rather than assuming `origin` or `main` (`.hai_env/agents/git-manager/SKILL.md:64`). However it is HAI-managed tooling, not a generic standalone Git assistant: every repository command requires enabled Git integration, service operations require GitHub integration, and repository work requires usable initialized HAI context (`SKILL.md:39–47`). Its owned `integrations.git`/`integrations.github` data belongs to the consumer environment (`conventions/git-configuration_conv.md:5–11`), so copying the agent must not copy or enable those settings. Commit-producing work also requires fresh per-operation recording verification, even if the answer is verified recording-disabled/no-obligation; source/coverage failures can block commits (`procedures/commit-and-export.md:25–39`, `:47–49`). That policy is a substantive usability tradeoff to document for adopters.

Git's helper has a real installation-layout coupling: `_INSTALLED_ROOT = Path(__file__).resolve().parents[4]` and imports of core startup/agent utilities (`scripts/validate_git_configuration.py:12–15`). It depends on those internal helper symbols remaining compatible. The package has no independent core/API compatibility declaration currently inspected. A flat `hai_agents_library/<name>` is one directory shallower than `.hai_env/agents/<name>`; direct source helper/tests would locate the wrong root. Testing staged installed copies avoids that; alternatively `hai_agents_library/agents/<name>` matches installed depth and makes shared relative paths easier to maintain. This is a layout choice, not a requirement for runtime to reference the library.

**Release-manager:** reusable for **HAI bundle maintainers**, not universally applicable to any product. Its purpose/scope explicitly releases HAI (`.hai_env/agents/release-manager/SKILL.md:11–26`), and local policy hardcodes `.hai/release-<version>.json`, `hai-<version>.zip`, HAI state/specification contracts and the agreed historical/0.x version rules (`conventions/release_conv.md:5–18`, `:43–46`, `:70–74`). It requires Git-manager through Leader for repository/service effects, while independent filesystem preparation can continue (`SKILL.md:18–20`, `:70–71`). Put it in the library with an accurate “HAI bundle release” scope. Making it a generic product release manager would be a separate adaptation, not an incidental rename or silent policy generalization.

## Golden source, installed snapshots and updates

The library should be authoritative for **upstream package development**; the installed copy should be authoritative for **that workspace's current execution**. Library updates must have no automatic effect on installed behavior. Updating an installation is explicit replacement/update work, distinct from updating its source package.

Recommended minimal v1:

1. Keep complete packages and a small README/index of purpose, dependencies, compatibility assumptions and install steps. The index is not a runtime catalogue. Use one repository/library revision for provenance initially; independent package SemVer and dependency resolution are optional later work.
2. Install selected whole-package snapshots into `.hai_env/agents/<name>` and explicitly register them. Never symlink, hardlink, import, or fall back to the library for live resources. Package-local files and installed peers/core are allowed runtime dependencies.
3. Record minimal install provenance outside package bytes, such as package name, source revision and baseline package digest. A small installation record or documented manual record is sufficient; no mandatory package manager, remote registry, signing infrastructure or online update service is needed for this step. Provenance must not become a runtime source path that is loaded to resolve behavior.
4. Do not silently overwrite a nonempty installed folder or local edits. Show source/base/installed differences; preserve a recoverable copy and apply an explicit user-selected update. The simplest first-version policy is stop on locally modified installations and require an explicit preserve/replace/merge decision. Automated three-way merges are optional.
5. Publish a local-edit rule: recommended default is edit shared behavior in the library, then update chosen installations explicitly; workspace-specific changes remain installed customizations with recorded divergence. Promotion from installed edits back into golden source is explicit review, never automatic synchronization.
6. Do not overlay updates that leave deleted old files behind. Stage and validate a full candidate package, coordinate a guarded replacement plus catalogue description synchronization, preserve/report partial results and retain a recoverable prior snapshot. Rollback is an explicit operation; compatibility/data migrations and unknown local state are not automatically undone by restoring an old definition folder.

Single-source maintenance does not mean the copies remain perpetually identical. This design intentionally trades live coupling for versioned divergence. It therefore needs a way to know what was installed and to review updates; manual provenance/diff is a viable initial solution.

Core compatibility, agent-definition format, helper/API expectations, model class/effort support and package-specific data compatibility are different checks. Keeping state format 2 or specification format 1 unchanged does not by itself prove an updated package works with an older HAI core. For v1, document supported core release/format expectations and validate against that core; do not invent a large dependency protocol before needed. Existing optional `compatibility`/metadata fields can carry explanatory compatibility information, but no inspected tool currently enforces a new per-package compatibility scheme.

## Distribution choices and practical disadvantages

The smallest coherent distribution change is **one HAI release unit containing core plus the library as uninstalled source**, with `.hai_env` excluded. Consumers install only chosen packages. This preserves one release version while achieving runtime optionality; it does not reduce download size or keep optional source bytes absent from every checkout. Another viable choice is core-only plus a separately acquired library; this more strongly separates distribution but requires acquisition instructions and a matching-version story. Independently versioned library packages are a further product decision: current release policy says independent package releases require explicit choice (`.hai_env/agents/release-manager/conventions/release_conv.md:5–8`).

Disadvantages to accept or address:

- Snapshot drift and duplicated files; fixes do not reach installed copies until updated.
- Local customizations complicate upgrades; source/installed conflicts and abandoned files need explicit handling.
- Optionalizing Agent-definition-manager adds bootstrap/recovery work and weakens availability when core state or workspace catalogue is invalid. Today framework roles are selectable without initialized state; workspace registrations are withheld on invalid core state (`.hai/conventions/agent_conv.md:5–7`; `.hai/tools/startup/startup_check.py:320–325`). Direct format inspection remains possible through shared core tools, but optional installed owner execution may not be available.
- Maintaining library and installed copies in this development repository creates two review surfaces. A source-only change does not test this workspace's live installed agent; an installed-only change does not fix the golden source.
- Git and release packages have real core/peer dependencies; “HAI-compatible” needs a documented compatibility target rather than a universal portability claim.
- Moving specification out of core breaks existing documented paths and changes clean-install availability even if data contracts remain unchanged. This is a user-visible distribution/upgrade change requiring release assessment; it does not inherently require changing state/specification format versions.
- A same-ZIP library keeps delivery simple but ships optional source anyway. A separate library release reduces core delivery size but adds matching-version and support complexity.

## Minimal migration sequence after decisions and authorization

1. Resolve the intended installed names, analysis-versus-implementation scope, source layout, distribution choice and fresh-install bootstrap policy. Define golden-source versus installed-edit authority.
2. Specify library/source-kind semantics in the relevant core conventions and definition-manager procedures, keeping two runtime origins and no library execution fallback. Retain generic shared tools in core.
3. Prepare complete source packages and corrected installed-layout references. Copy Git/Release into the library without removing their installed definitions. Stage the two outgoing core packages as workspace snapshots and validate before switching registrations.
4. Under the currently valid registered owner, coordinate authorized core-folder/registration removal with installed-folder/registration creation. Avoid a second same-name registered or unregistered runtime definition. Preserve a recoverable baseline and report any partial state rather than claiming multi-file atomicity. The owner should remain able to finish its scoped self-migration; future bootstrap must not depend on this one-time circumstance.
5. Update core optional-package links/absence behavior, Release-manager installed peers and candidate-source contract paths, current installation docs, library distribution allowlist and current candidate notes/manifest policy as required by the chosen distribution. Preserve historical release artifacts and work records.
6. Verify both source packages and installed snapshots in a clean temporary core/environment layout. Reuse specification relocation and Git configuration fixtures; verify catalogue equality and relevant structural/manual links. Add the meaningful architectural check: an installed fixture still validates/operates when the fixture's library is removed, and source-only edits do not change installed bytes/behavior. Do not test by renaming or deleting the user's real library.
7. Report installed names/versions, explicit registrations, unchanged feature/integration flags, validation evidence and migration limits. No release publication, commits or pushes follow implicitly from this migration.

Untouched unless separately requested: Environment-manager/Activity-manager responsibilities, Leader's ordinary exclusive orchestration, state schema/version and current settings, profiles/model selections, Activity/transcript history, existing product specifications, Git credentials/remotes/integration switches, advisor, historical released assets, and the actual publication state.

## Outstanding choices that materially affect implementation

1. Does the duplicated name mean install **Specification-manager and Agent-definition-manager**, while keeping the already installed Git/Release agents? If not, which exact names?
2. Is the next step still analysis/design, or should an agreed migration be implemented after this review?
3. Should the library ship in the same HAI bundle as uninstalled source, be acquired separately, or remain repository-only initially? This determines package allowlist and manifest meaning.
4. For a fresh workspace with no Agent-definition-manager, is v1 a documented human copy/registration bootstrap, or a narrow core install helper authorized to copy/validate/register selected packages? Invoking the library manager directly is incompatible with the stated runtime rule.
5. Should installed edits be permitted workspace forks, with updates stopping on differences, or should all shared edits first go into the library? What may be promoted back upstream?
6. Is `hai_agents_library/agents/<name>` acceptable to preserve current relative depth, or is a flat package layout preferred with staged-install validation? Both can meet the no-runtime-library-dependency requirement.
7. Is the runtime prohibition specifically about loading/importing agent instructions/tools/contracts from the library, while explicitly authorized installation, source maintenance, tests and candidate packaging may read it as data? This distinction is necessary for a maintainable golden source.

The architecture can be implemented without refactoring the other three core roles or building a package manager. The decisions above prevent the first migration from silently creating an unusable fresh-install path or an accidentally mandatory library dependency.
