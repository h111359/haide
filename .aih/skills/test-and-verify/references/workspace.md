# Workspace and authority contract

Engine path references use `backend:src/service.py`, with workspace revision retained in the owning record. The standalone structured encoding is `{ "root": "backend", "path": "src/service.py", "workspace_revision": 3 }`. Both identify the same root/relative-path pair. Resolve it against its recorded registry mapping. `path` is a relative slash-separated path without `..`, an absolute prefix, drive prefix, backslashes or a NUL. Root ID `home` identifies the canonical parent of the sole installed `.aih/` and central `.aih_product/`. Home is always writable and cannot be removed or relocated through ordinary registry administration. Additional IDs are stable and never reassigned to unrelated content.

A registry entry contains `id`, `name`, canonical absolute `path`, `purpose`, and `access` (`read-write` or `read-only`). Accessibility observations, diagnostics and baseline freshness are separate from selected access. Root paths are disjoint: duplicates, ancestors/descendants, and ambiguous filesystem aliases are invalid. A root's parent never becomes authorized. Links, junctions/reparse points and multiply linked files are rejected when final containment cannot be established. Resolve existing parents and targets; validate both sides of move/delete, and recheck identity at use. Reject changed targets. Windows operations that lack a tested secure backend must block with a diagnostic.

All managed effects, including test output, subprocess homes/caches/temp/config/bytecode, permission changes, browser profiles and cleanup, require current writable registration plus action-specific scope. Disable bytecode. Installed runtimes can be read without permission to modify their installation, home or credential caches. An unconstrained subprocess is not safe merely because its working directory is inside a root. If the host cannot enforce the roots and access modes, the tool is unavailable. External user applications remain outside AIH's control; never claim otherwise.

Only deliberate human administration can revise membership/access. Every accepted registry change requires an idle owner and expected state revision, preserves old mappings in the ledger, and invalidates affected scope, baseline, analysis, plan authorization, docs and tests. Unknown impact remains unresolved. It neither starts an agent nor grants implementation authority. Idle changes are allowed with an open request; core maintenance is not. Adding/relocating a root requires explicit documentation reconciliation before implementation uses it. Removal never deletes source files, failing tests, defects or historical evidence.

Cross-filesystem effects have per-root checkpoints; there is no atomic cross-filesystem commit. Recovery validates current permissions. A removed/restricted root blocks prohibited recovery writes instead of restoring old authority. Temporary data is operation-owned and disposable. `.aih_product/tmp/` contains inert data only; durable evidence/authorization is stored in its owning record. Executable temporary fixtures live in expressly authorized ordinary workspace folders.
