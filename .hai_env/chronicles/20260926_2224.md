## Outcome:

I recommend **a fixed structure organized by the function of each instruction**. The same headings should appear in every prompt, while task-specific detail belongs in subsections.

The important part is not just naming the sections: **each section needs an explicit ownership rule**. Otherwise, “Requirements,” “Instructions,” and “Constraints” gradually become interchangeable containers.

Your current prompts show this problem:

- `merge_context.md` puts input validation, filesystem boundaries, and blocking conditions under “Required inputs.”
- “Independent verification and save” combines review, concurrency, recovery, saving, and final reporting.
- `extract_context.md` separates more concerns, but “Output folder and replacement contract” still combines result structure, execution rules, and permissions.

Here are three viable alternatives.

**Option A — Organize by instruction function. Recommended.**

This is the strongest choice for quickly finding and revising a particular instruction.

```markdown
---
# Framework metadata and parameter schema
---

# Prompt title

## 1. Objective
## 2. Context
## 3. Inputs
## 4. Outputs
## 5. Rules
## 6. Procedure
## 7. Verification
## 8. Failure and uncertainty
## 9. Examples
```

Each section answers exactly one question:

| Section | Question it answers | What belongs here |
|---|---|---|
| **Objective** | What should this task accomplish? | Intended outcome, scope, explicit exclusions. |
| **Context** | What background is needed to understand the task? | Relevant facts, terminology, relationships, rationale. No behavioral instructions. |
| **Inputs** | What does the task receive or need? | Parameters, reference material, prerequisites, defaults, interpretation of input values, validity conditions. |
| **Outputs** | What must the task deliver? | Artifacts, response contents, destinations, schemas, formatting, language, tone, and audience. |
| **Rules** | What governs the work and its decisions? | Interpretation rules, decision criteria, permissions, prohibitions, evidence standards, and preservation obligations. |
| **Procedure** | In what order should the work happen? | Steps, dependencies, branches, iterations, and checkpoints. |
| **Verification** | How is an acceptable result established? | Checks, evidence of correctness, review method, reviewer independence, and completion criteria. |
| **Failure and uncertainty** | What happens when normal completion is not possible? | Clarification, blocking, retry, partial-result, recovery, and escalation behavior. |
| **Examples** | What does correct application look like? | Illustrative inputs, outputs, and edge cases. No additional binding instructions. |

For longer prompts, standardize the subdivisions of **Rules**:

```markdown
## 5. Rules

### 5.1. Interpretation and evidence
### 5.2. Decisions and transformations
### 5.3. Permissions and preservation
### 5.4. Interaction and resource limits
```

These subdivisions accommodate research, implementation, creative writing, analysis, review, planning, and interactive dialogue. A simple writing prompt might use only one subsection; a filesystem operation might need all four.

**Advantages:** predictable placement, easy comparison between prompts, easy targeted revision.

**Tradeoff:** reading the execution sequence sometimes requires following references to rules defined elsewhere.

**Option B — Organize by execution phase.**

This is useful when people primarily read prompts as operating procedures.

```markdown
---
# Framework metadata and parameter schema
---

# Prompt title

## 1. Objective and scope
## 2. Rules applying throughout
## 3. Prepare
### Inputs and context
### Preconditions

## 4. Perform
### Working method
### Decisions and branches

## 5. Check
### Acceptance criteria
### Verification method

## 6. Deliver
### Output contract
### Saving or handoff

## 7. Handle interruptions and failure
## 8. Examples
```

The placement rule is:

> Put an instruction in the phase where it takes effect. Put instructions that apply across phases in “Rules applying throughout.”

For extraction, the flow becomes:

`Prepare sources → Extract findings → Check coverage → Deliver the verified folder`

For a conversation prompt, “Perform” can define a repeating dialogue cycle, and “Deliver” can define individual responses and the closing result.

**Advantages:** natural reading order, clear operational flow, convenient for running a task manually.

**Tradeoff:** less convenient for revising one concern across the whole prompt. Evidence rules or output requirements can easily become scattered unless the placement rule is enforced carefully.

**Option C — Organize as a compact contract.**

This is suitable if you prefer fewer top-level headings and are comfortable with larger sections.

```markdown
---
# Framework metadata and parameter schema
---

# Prompt title

## 1. Purpose
## 2. Given
## 3. Required result
## 4. Governing rules
## 5. Execution
## 6. Acceptance
## 7. Exceptions
## 8. Examples
```

Its ownership rules are:

- **Purpose:** objective and scope.
- **Given:** descriptive context, supplied inputs, and prerequisites.
- **Required result:** deliverables and their exact representation.
- **Governing rules:** constraints, decision logic, and authority boundaries.
- **Execution:** workflow.
- **Acceptance:** verification and completion conditions.
- **Exceptions:** behavior when information is missing or execution cannot proceed.
- **Examples:** illustrations only.

**Advantages:** compact, readable, applicable to both simple and complex prompts.

**Tradeoff:** “Given” combines background and inputs. For your framework, where parameters already have a formal schema, separating those concerns as in Option A would be clearer.

| Your priority | Best fit |
|---|---|
| Find and revise an instruction quickly | **A** |
| Follow a task step by step | **B** |
| Keep the document visually compact | **C** |

**The placement rules I would adopt with Option A**

These rules are what make the structure stable.

1. **Give each instruction one authoritative home.**  
   Other sections reference it instead of repeating it. The procedure says “Validate the inputs against §3”; it does not restate every input condition.

2. **Split sentences that perform different functions.**  
   “Require two readable files; if either is missing, ask and stop” contains two instructions:
   - **Inputs:** two readable files are required.
   - **Failure and uncertainty:** missing required files trigger clarification and block execution.

3. **Separate result properties from decision logic.**  
   - “Entries use positive integer IDs” → **Outputs**.
   - “Preserve existing IDs and allocate new IDs above the current maximum” → **Rules**.
   - “Build the request-to-product ID mapping before translating references” → **Procedure**.
   - “Check that every reference resolves” → **Verification**.

4. **Separate permissions from workflow.**  
   - “The request folder is read-only” → **Rules**.
   - “Save only after verification passes” → **Procedure**.
   - “Restore the previous set if saving fails” → **Failure and uncertainty**.

5. **Keep context descriptive.**  
   “Product definitions preserve the evolution of accepted decisions” is background.  
   “Superseded entries MUST remain in the product files” is a rule.

6. **Keep examples non-authoritative.**  
   Every requirement demonstrated by an example must already be stated in its proper section. Examples must not introduce hidden defaults, exceptions, or permissions.

7. **Treat contradictions as errors, not as section precedence.**  
   “Rules” should not silently override “Outputs,” or vice versa. Conflicting instructions need correction.

8. **Keep the headings stable without inventing content.**  
   Use “None” or “Not applicable” when a section has no task-specific content. Do not invent an agent role, mandatory tools, independent review, or a detailed workflow merely to fill the template.

The distinction between **classification rules** and **output format** matters here: deciding that something is a technical decision belongs in Rules; specifying how that decision is written belongs in Outputs.

**Keep the YAML header as a separate framework layer**

Your prompts already have machine-readable metadata. I would preserve that separation:

- **YAML:** identity, parameter schema, invocation template, and concise output/effect declarations.
- **Markdown:** the human-readable task contract.

The reusable instructions for invoking prompts should eventually have one framework-level home, provided the framework reliably supplies them during execution. Otherwise, standalone prompts still need that guidance.

**My choice is Option A:** it best supports your main requirement—knowing immediately where an instruction belongs and where to find it later. It is universal as an organizing structure, while allowing each task to define its own rules and level of detail.

## Prompt:


Explain the benefits of schema version and ID in convention\_prompt\_format.md file. What if this conversion omits them? 


## Outcome:

Both fields help **software manage prompts**. Neither is necessary for an AI or a person to understand the prompt.

**`schema_version` identifies the format of the YAML header.**

For example, version 1 might represent `output.format` as a string. A future version could replace it with a list or reorganize the input definitions. The version lets a reader or validator select the correct interpretation—or reject an unsupported format clearly.

It does **not** identify revisions to the prompt’s instructions. Changing extraction rules would not change `schema_version`; changing the header’s structure or interpretation could.

If omitted:

- A framework using one fixed header format can work perfectly well.
- Future incompatible changes require updating all prompts together, detecting formats from their fields, or maintaining compatibility without an explicit version.

Its benefit depends on tooling actually checking it. Merely including the field does not provide compatibility.

**`id` identifies the prompt independently of its filename and location.**

For example:

```yaml
id: extract_context
```

The file could move from `definitions/extract_context.md` to `prompts/extraction.md` while retaining that identity. A catalog, execution history, or configuration could associate both locations with the same prompt.

If omitted:

- The framework can identify prompts by their paths.
- Moving or renaming a file changes that identity unless references are updated or another tracking mechanism exists.
- There is no ID uniqueness rule to maintain, and no possibility of accidentally copying an ID into a different prompt.

The current invocation template selects the prompt **by path**, so the ID does not itself make invocation survive a file move.

| Field | Main benefit | Reasonable to omit when |
|---|---|---|
| `schema_version` | Explicit compatibility across header-format changes | You maintain one format and update prompts together |
| `id` | Stable identity across file moves and renames | File paths are sufficient identifiers |

**For your framework, I would keep `schema_version` and make `id` optional until something actually uses it.** Versioning is inexpensive preparation for evolving a structured format. A separate identity becomes useful when catalogs, saved configurations, or execution histories reference it.

If your priority is maximum simplicity, omitting both is also reasonable. The convention should then explicitly state: **all prompts use the current header format, and each prompt is identified by its workspace-relative path.**

For YAML parameter keys, these are the main alternatives:

| Style | Examples | Characteristics |
|---|---|---|
| **camelCase** | `requestId`, `sourceFiles`, `productFolder` | Compact, widely used in structured data and code. |
| **kebab-case** | `request-id`, `source-files`, `product-folder` | Readable, visually separates words. Some programming languages require bracket notation to access these keys. |
| **PascalCase** | `RequestId`, `SourceFiles`, `ProductFolder` | Clear word boundaries; commonly associated with type or class names. |
| **Words with spaces** | `Request identifier`, `Source files`, `Product folder` | Most natural for humans, but less convenient for programmatic access and consistent capitalization. |
| **lowercase without separators** | `requestid`, `sourcefiles`, `productfolder` | Simple, but longer names become difficult to read. |

All are valid YAML key styles. Compatibility with framework tooling is a separate consideration.

**I recommend camelCase** for your convention: `requestId`, `requestFolder`, `productFolder`. It avoids underscores while remaining compact and convenient for automation. Human-facing labels can still use ordinary language:

```yaml
inputs:
  requestId:
    type: string
    required: true
    label: Request identifier
    description: Unique identifier for the request.
```

If your preference is stronger visual separation between words, **kebab-case** is the best alternative.

The current convention’s explicit snake-case requirement applies to parameter names. Whichever style you choose should apply consistently to authored keys in both `inputs` and `invocation.inputs`. Fixed schema keywords such as `minLength` and `minItems` should retain their defined spelling.

## Prompt:

what is the difference between snake-case and camel-case


## Outcome:

**snake_case** separates words with underscores; all letters are lowercase:

```yaml
request_id:
source_files:
product_folder:
```

**camelCase** joins words without separators; the first word is lowercase, and each subsequent word starts with a capital letter:

```yaml
requestId:
sourceFiles:
productFolder:
```

The difference is naming style, not functionality. Both work as YAML keys, but their spelling must match wherever referenced.
