# HAI 0.4.0

This experimental release adds Activity communication, invocation workspaces,
usage reporting, durable source recording, startup guidance and general work/output
boundaries. Version 0.4.0 follows the established experimental 0.x policy.
Actual publication and downloadable assets are tracked separately on GitHub Releases.

## Changes

- Activity-local append-only agent chat with validated read/post operations and
  attributable handoffs. Shared chat does not replace decisions or chronicles.
- Runtime-allocated working folders for every new agent invocation. Same-instance
  follow-ups retain their allocation; new spawns receive a new one. The host records
  actual handles and verifies stopped writers before closure.
- Activity usage records with source-bounded token observations, separately labeled
  optional credit estimates and automatic refresh before closure. Unknown charges
  remain unavailable rather than fabricated zeroes.
- Core source-backed chronicle synchronization, exact source/range attribution,
  current-session discovery, hash/checkpoint verification and commit/closure checks.
  Recording uses eligible saved exchanges, not reconstructed conversation text.
- A compact startup/Help overview combining current Activity state, supported task
  choices and every registered agent. Startup alone waits for a choice; a concrete
  task can proceed without an extra menu selection.
- Explicit role execution/delegation and independent-review requirements, preserving
  actual host model/tool capability checks and owner boundaries.
- A framework-wide workspace write boundary, including scratch, caches, cleanup,
  linked destinations and indirect tool writes. Outside locations/purposes require
  explicit covering user permission.
- Artifact ownership and placement for all HAI work: software, documents, research,
  flows and operations. Requested outputs retain established destinations; task
  working material and execution evidence belong with the Activity/invocation unless
  explicitly designated otherwise. Reusable tests and fixtures remain product resources.

## Breaking operating and layout changes

Fixed environment configuration now lives at:

- `.hai_env/config/state.json`
- `.hai_env/config/agent_instructions.md`
- `.hai_env/config/model_profiles.json` (optional)

Earlier `.hai_env/state.json`, `.hai_env/agent_instructions.md` and optional
`.hai_env/model_profiles.json` are migration inputs only. Startup never relocates
those files or initializes competing defaults. Existing environments must follow
[explicit layout migration](../.hai/procedures/migrate-environment-layout.md).

Safely apply legacy instructions before migration, stop other writers, inspect the
preview and authorize `environment migrate-layout --apply` separately. Exact bytes,
schema versions and unrelated records are preserved; recovery copies and a manifest
record actual partial effects. Mixed/conflicting layouts or interrupted operations
require reviewed resolution. Do not change a version marker to bypass migration.

New source/assignment checks can block recording, commits or closure when required
source evidence is missing or ambiguous. Additional workspace/output permission and
placement rules apply to instruction-driven behavior even when no Python API changes.

## Compatibility

| Boundary | Target |
| --- | --- |
| Bundle/tag/asset | `0.4.0` / `v0.4.0` / `hai-0.4.0.zip` |
| Python | 3.11 or newer; standard-library core |
| Current environment state format | `3` |
| Recognized environment state formats | `[2, 3]` |

The [current manifest](../.hai/release-0.4.0.json) snapshots the unchanged owning
[state declaration](../.hai/contracts/state.json). Format 2 remains read-only
specification-migration context; layout relocation does not perform that separate
conversion. Format-1 conversion is not automated. Bundle SemVer, state format and
agent configuration versions remain independent.

The established experimental 0.x policy selects a MINOR increase for new capabilities
and breaking changes; 0.3.1 would understate this release. Preserve `.hai_env/`,
settings, product data and local core customizations before replacement. Follow
[installation/upgrade instructions](../INSTALL.md) and the
[configuration migration guide](agent-configuration-migration.md) for applicable
owner operations.

## Scope of the downloadable bundle

The core ZIP contains reusable `.hai/`, the MIT license and required same-commit
documentation. It excludes `.hai_env/`, saved settings/profiles, Activities,
chronicles, `.git/`, generated work and the optional `hai_agents_library/`.
Historical manifests outside `.hai/` are repository evidence, not shipped current
release identities. Exactly one manifest, `.hai/release-0.4.0.json`, is current.

The same repository revision also contains improved optional Business analyst,
Solution architect, Software developer and backlog packages. The architect/developer
workflows include assessments, explicit decisions, standalone plans, directive
checks and verification evidence; task-specific coverage reports were moved to
their owning Activity. Those optional packages are not included in the core ZIP
and require separate reviewed installation from the corresponding source checkout.

## Validation and publication status

Core validation on Linux/Python 3.12.3 ran 291 tests: 289 passed and two
platform-specific checks were skipped. All six core suites completed successfully.
The stale developer-procedure fixture now follows the indexed procedures, and a
broken tooling-concept heading link is corrected. Tests requiring actual optional
agent packages explicitly skip when those packages are absent from the core-only
ZIP; they continue to execute in the repository. This adds no optional-package
dependency to normal core use.

Exact source, release checks, archive inspection and SHA-256 are recorded separately
as release readiness evidence. A source tree or tag alone is not publication or
download verification. Linux is the preparation platform; Windows/macOS and live
model/UI compliance must not be inferred from structural fixtures.

No release workflow is added, and no public tag, push, draft or release is created
by these notes. Publication instructions and assets are prepared separately after
the release-source identity is frozen.
