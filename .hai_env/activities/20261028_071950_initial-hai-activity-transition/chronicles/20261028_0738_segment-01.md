**I support broadening “requests” into “iterations.” I would not automatically create a new iteration every time the leader is summoned.** Those are two separate changes, and the first is stronger than the second.

Your idea addresses a real limitation: meaningful work does not always produce an implementation. Brainstorming, investigating a problem, comparing approaches, or making a decision can all be complete and useful outcomes.

The current request model already allows discussion and skipping preparatory stages. However, its [completion rule](/home/hromar/Desktop/repos/haide/.hai/agents/request-manager/conventions/request_conv.md:52) requires verified implementation. Renaming it would leave that underlying mismatch intact.

I would shape the concept around three principles:

1. **An iteration has a purpose and an outcome, rather than a mandatory sequence.** Clarification, analysis, planning, implementation, and verification remain available. Use the steps appropriate to the work. Brainstorming might finish with alternatives and tradeoffs; investigation with findings; implementation with tested changes. Each can legitimately be completed.

2. **Starting the leader establishes continuity; it does not necessarily start new work.** If you restart a chat after an interruption, provide a clarification, or ask for status, you probably want to continue the same iteration. Creating another would fragment its history. The current model also permits only one open request, so automatic creation would immediately raise the question of what happens to unfinished work. My recommendation: resume the relevant iteration by default; create one when a distinct objective begins or you explicitly request a new cycle.

3. **Keep records proportional to the work.** A short exploration should not require empty definition, analysis, and implementation documents. Record its purpose, useful findings, decisions, and outcome; add plans and other artifacts when needed. Separate lifecycle—active, waiting, closed—from activities such as analysis or implementation.

I also see a tension in the existing rule that permanently freezes preparatory documents after the first implementation attempt. That preserves history, but iterative work often changes the understanding and plan. Preserving earlier versions while allowing explicit revisions would fit your proposed concept better.

**My reservation about the name:** “iteration” usually means a cycle toward a larger objective. It works well if that is what you intend. If it means any arbitrary collection of activity, it becomes vague. A useful definition would be:

> An iteration is a bounded cycle of work pursuing an intended outcome. It may include exploration, clarification, analysis, planning, execution, and verification as needed.

Under that definition, this conversation could be an iteration whose outcome is a considered design recommendation. It would not need implementation to count as successful.

I would therefore pursue the conceptual change, but avoid a global word replacement or tying iteration boundaries to chat boundaries. **Make purposeful work the organizing unit, with the leader responsible for maintaining continuity.**
