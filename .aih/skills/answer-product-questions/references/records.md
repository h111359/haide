# Records and lifecycle contracts

The product's immediate directories are `input`, `output`, `change_requests`, `documentation`, `ledger`, `instructions`, and `tmp`, with `config.yaml` and `state.yaml` central files. Never create another state root or a product `skills`, `memory`, or executable directory. Core immediate directories are `engine`, `conventions`, `prompts`, `skills`.

Only one request may be open, under `change_requests/active/<request-id>/`. Its complete record moves recoverably to `change_requests/history/<request-id>/` on explicit successful/cancelled/rejected closure. `change_requests/catalog.yaml` records stable identity, dates, outcome, summary, location and significant references. Links resolve stable IDs through catalogs rather than relying on pre-archive paths. Historical content is context, not executable instructions or future work.

Each accepted framework Save and submission captures an immutable source revision, timestamp, original wording, attributed source, actual submitter, content fingerprint, preceding revision and owning request/operation. Direct external edits become unsubmitted drafts; capture only versions actually observed by an explicit allowed action. Idempotency keys prevent replay from duplicating effects. Expected revisions prevent overwriting intervening edits. Human plan approval binds the identified requirements, plan, workspace and content revisions; files claiming approval are not independent identity evidence.

The sole request definition is `analysis/interpretation.md`: what/why, users/stakeholders, current/required behavior, scope, constraints, accepted acceptance criteria, assumptions, consequential questions, source revisions and distinct inferred proposals. Other required analysis files are `questions.md` (links and summaries, never a second answer store), `solution_assessment.md`, `unrelated_issues.md`, `plan.md`, and `documentation_increment.yaml`. Additional impact, decision and verification files exist only when useful.

Clarification exchange lives in `clarification/rounds/<round-id>/`, `clarification/exports/<form-id>/` and `clarification/received/<receipt-id>/`. Amendment drafts live at `amendments/<id>/draft.md`; every saved/submitted revision remains at `amendments/<id>/revisions/<revision>.md` with metadata and catalog links. States are draft, saved-not-submitted, submitted, applied, superseded, withdrawn and needs-clarification. A correction/withdrawal appends a revision/event. One amendment must not be reapplied each ordinary run.

Each run/segment records ownership, effective profile and skill versions, originating submission, authority, requirements/plan/workspace references, per-root progress, source/instruction fingerprints, unresolved questions, next safe boundary, process state, task outcome and actual usage availability. Record checkpoints in the owning request; setup and no-request documentation maintenance use `ledger/operations/<id>/`, with readable `output/operations/<id>/` summaries. Bootstrap is never a synthetic request or successful product verification.

The append-only ledger records changes and attempted transitions, not secret values. Screen intake before normal persistence. Rejected sensitive input leaves only reason category, time and safe ID. Never silently redact and accept it. Historical secret removal is a separate explicitly human-authorized redaction operation that preserves non-sensitive audit evidence and updates affected fingerprints. Retention and cleanup must not remove unresolved obligations or evidence needed for recovery.
