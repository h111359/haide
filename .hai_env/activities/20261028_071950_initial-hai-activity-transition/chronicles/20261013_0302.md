## Prompt:

Compare json and yaml for storing local app state on convenience for AI and human work, possibility to store different values, including big text chunks, easiness to be maintained automatically via scripts, usefullnes, community preferences, popularity.


## Outcome:

**For local app state, I’d default to JSON. Choose YAML when people frequently edit the file directly, especially if it contains comments and long text.** The key distinction is who maintains the file: application code, humans, or both.

| Criterion | JSON | YAML |
|---|---|---|
| Human readability | Clear but more punctuation and quotes | Usually cleaner for small, descriptive documents |
| Human editing | Predictable syntax; commas and escaping can be annoying | Convenient comments and multiline text; indentation and implicit types can cause mistakes |
| AI reading and editing | Simple grammar makes validation straightforward | Readable and concise, but more syntax choices and indentation sensitivity |
| Automatic script updates | Excellent fit for parsing, changing values, and serializing | Easy to update data; preserving comments and formatting needs suitable tooling |
| Values supported | Strings, numbers, booleans, null, arrays, objects | Same everyday values, plus advanced features and additional types depending on schema/parser |
| Large text chunks | Supported, but newlines and quotes must be escaped | Literal blocks make embedded prose, Markdown, and code easier to read |
| Comments | Unsupported in standard JSON | Supported |
| Consistency across tools | Generally strong with basic types | Requires more attention to parser version, implicit typing, and tags |
| Typical usefulness | Saved state, caches, metadata, interchange | Human-maintained configuration, workflows, documents with embedded text |

JSON’s types and syntax are defined by [RFC 8259](https://www.rfc-editor.org/info/rfc8259/). YAML’s comments, block strings, tags, and other features are defined in the [YAML specification](https://yaml.org/spec/1.2/).

**For AI work, distinguish reading from reliable writing.** Both formats are practical inputs for AI. YAML may be easier to scan when the content is mostly prose; JSON is easier to constrain and validate when generating updates. That is an engineering judgment, not a universal claim that models perform better on JSON. A schema and a parse/validation step matter more than the format alone. Editor validation and completion are available for both through [SchemaStore](https://www.schemastore.org/).

**For big text chunks, YAML has a clear editing advantage.** These represent the same string:

```json
{
  "notes": "First paragraph.\n\nUse \"preview\" before publishing."
}
```

```yaml
notes: |-
  First paragraph.

  Use "preview" before publishing.
```

In YAML, `|` preserves line breaks, while `>` folds ordinary line breaks into spaces. The `-` in `|-` removes the final newline. Choose these deliberately if exact text matters. Neither format has a universal small text-size limit; practical limits come from the parser and application. [YAML block scalar rules](https://yaml.org/spec/1.2/)

If the text is large and edited independently—prompts, notes, generated reports—I’d usually put it in a separate `.md` or `.txt` file and keep its path in the state.

**For scripts, JSON is the lower-maintenance choice.** Its limited syntax fits a simple read → modify → write workflow, and environments such as Python provide a standard-library implementation. YAML introduces another concern: ordinary serializers may preserve the values while changing layout, removing comments, or changing string styles. Libraries with round-trip support, such as `ruamel.yaml`, help when humans and scripts share ownership of a file. [Python JSON documentation](https://docs.python.org/3.13/library/json.html), [ruamel.yaml documentation](https://yaml.dev/doc/ruamel.yaml/)

For either format:

- Parse and serialize rather than updating with regex or string replacement.
- Validate types and required fields; include a `schema_version` for migrations.
- Write through a temporary file and replace the original atomically where supported.
- Coordinate concurrent writers; neither format provides transactions or locking.

**YAML’s extra expressiveness rarely benefits ordinary app state.** Dates, binary data, sets, and custom types can be represented through YAML tags and schemas, but support varies. For portable state, use explicit conventions in either format: ISO date strings, string IDs, and deliberate encodings for binary data. Large integers also need care across languages; JSON’s specification highlights interoperability limits around common floating-point implementations. [RFC 8259](https://www.rfc-editor.org/info/rfc8259/)

With YAML, use a safe loader, standardize the parser/schema, and quote ambiguous strings. In particular, YAML 1.1 and 1.2 implementations can interpret unquoted values differently. [ruamel.yaml parser examples](https://yaml.dev/doc/ruamel.yaml/basicuse/)

**Community preference depends on the ecosystem.** Both are established choices: npm uses JSON for package metadata, while GitHub Actions uses YAML for workflows. These demonstrate adoption, but do not establish a global popularity ranking or prove developer preference. I wouldn’t attach a percentage to “JSON versus YAML popularity” without defining what is being counted. [npm documentation](https://docs.npmjs.com/creating-a-package-json-file/), [GitHub Actions documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)

My recommendation for your use case:

| Situation | Choice |
|---|---|
| State written mostly by the app or scripts | **JSON** |
| Configuration edited mostly by humans | **YAML** |
| Humans and AI regularly edit embedded prose | **YAML**, with validation and comment-preserving tooling |
| Structured state plus substantial documents | **JSON + separate Markdown/text files** |
| Frequent writes, concurrent writers, or transactional updates | Consider **SQLite** |

For a typical local app, **`state.json` plus separate text files** gives the strongest balance of automation, portability, and human/AI convenience.
