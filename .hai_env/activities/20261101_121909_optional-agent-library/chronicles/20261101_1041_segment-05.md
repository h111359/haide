## Outcome:
**Not all five agents need to be mandatory core agents.** My recommendation is to keep coordination, environment/bootstrap, and Activity continuity as core capabilities—but stop treating each capability as requiring a separately spawned agent.

Specification management and agent-definition authoring are the strongest candidates for optional installation.

The important distinction is between:

- **Responsibility:** who owns a capability and its rules?
- **Module:** where its procedures, contracts, and tools live.
- **Worker:** whether a separate agent executes a particular task.
- **Installation:** whether every workspace receives it.

The current architecture couples these decisions more tightly than necessary.

| Current agent | Recommendation | Reason |
|---|---|---|
| **Leader** | Keep in `.hai` as the root coordinator. | Task boundaries, specialist selection, dependencies, and user decisions are fundamental to HAI orchestration. |
| **Environment-manager** | Keep its capability and contracts in core; make routine execution available to Leader. | Every HAI installation needs environment handling, but routine validation/configuration does not inherently require another agent. |
| **Activity-manager** | Keep core record/lifecycle functionality; narrow the role. | Activities are mandatory under current HAI policy. Their continuity and write coordination deserve clear ownership, but arbitrary implementation does not belong to record management. |
| **Specification-manager** | Make an optional reusable package, installable in `.hai_env/agents`. | Not every workspace needs HAI’s specification system. The package already explicitly supports standalone use. |
| **Agent-definition-manager** | Make authoring and architectural review optional; retain basic registration/validation infrastructure in core. | Workspaces must be able to execute installed agents without requiring an agent-authoring specialist. |

**Optional does not necessarily mean workspace-specific.** None of these five roles is inherently specific to this repository. Specification-manager, for example, is reusable across many workspaces while still being unnecessary in others.

Therefore `.hai_env/agents` can be the installation location for an optional package, but I would avoid turning every installation into an independently maintained copy. Reusable packages should retain an upstream source and version; genuinely local policies and domain roles belong to the workspace.

**Environment management should be a Leader-accessible core module, not necessarily a separate worker.**

Your intuition is largely correct: environment handling is part of establishing and maintaining the context in which Leader operates.

However, merging all environment instructions into Leader’s main definition would create a different problem: a large coordinator carrying initialization, migration, configuration, and recovery details continuously.

A better arrangement is:

- Keep environment schemas, validation tools, and procedures separately maintained.
- Let Leader load and execute routine procedures when needed.
- Delegate complex migrations or repairs when a separate context or review provides value.

The existing read-only startup helper already demonstrates this approach. Today, broader direct execution is prohibited by [Leader’s rules](/home/hromar/Desktop/repos/haide/.hai/agents/leader/SKILL.md:26), so this is a proposed policy change.

Moving Environment-manager into `.hai_env` would be the wrong simplification. Environment initialization must remain available before the workspace environment and its agent catalogue are usable.

**Activity-manager can work without invoking Environment-manager. It cannot currently work without valid environment information.**

Its actual dependency is:

> Activity operation → validated store location and compatible configuration

It is **not**:

> Activity operation → summon Environment-manager first

Leader can obtain the required evidence from the startup helper and pass it directly to Activity-manager. The latter then performs its own record/path checks. That relationship is explicit in its [discovery procedure](/home/hromar/Desktop/repos/haide/.hai/agents/activity-manager/procedures/discover-and-create.md:15).

Consequently, removing Environment-manager as a separate worker is viable if its configuration and initialization functions remain available elsewhere. Removing those functions entirely is not.

The reverse dependency also needs care: environment bootstrap must work before an Activity exists. Ordinary later configuration can remain tracked within an Activity. The existing bootstrap exceptions already recognize this ordering.

**Activity-manager currently combines two responsibilities that should be separated.**

It owns records, lifecycle, transcripts, and continuity—but also performs general analysis, planning, implementation, and verification. See its [scope](/home/hromar/Desktop/repos/haide/.hai/agents/activity-manager/SKILL.md:15).

That makes it both a record keeper and a general task executor.

I would retain the former and remove the latter from its identity. Otherwise:

- Record ownership becomes confused with ownership of the actual subject matter.
- Routine bookkeeping uses the same advanced/high worker as substantive execution.
- The role becomes a default destination for work that has no specialist.

A focused Activity worker can still be useful for transcript processing, history preservation, and serialized writes. Simple record operations may instead be deterministic tools.

After narrowing it, **Leader should be allowed to perform short ordinary tasks directly**, delegating when expertise, context separation, parallel work, or review justifies it. Introducing another compulsory general-purpose worker would reproduce the same overhead.

**Specialists can operate without Leader in some senses, but they are not autonomous orchestrators.**

The shared conventions permit directly called specialist roles. A human can supply the required inputs; the specialist can perform its own work and return dependencies to that human. Specialists cannot summon other agents themselves.

However, direct invocation does not erase registration, environment, Activity, permission, or feature requirements. Some Activity procedures also explicitly rely on Leader for source attribution and boundary decisions, so that workflow is not fully independent.

Specification-manager has the strongest independence: its [standalone-use rule](/home/hromar/Desktop/repos/haide/.hai/agents/specification-manager/SKILL.md:40) explicitly permits operation without HAI, Leader, state, profiles, or Activities. It also prohibits using “standalone” as a loophole around disabled HAI-managed specification work.

**There are several different reasons an agent might not be usable in a session.**

| Situation | Actual effect |
|---|---|
| No need for its capability | The agent is unnecessary, not unavailable. Most Activities need no specification or definition-authoring work. |
| Unregistered role or invalid definition | It cannot be selected for execution. It may still be inspected as data. |
| Missing profiles or unsupported model/effort | Normal delegated invocation is blocked. Leader’s helper still works; Environment-manager has a narrowly defined startup bootstrap exception. |
| Invalid environment or unavailable mandatory instructions | Dependent work is blocked; bounded diagnosis and authorized setup/repair remain possible. |
| Specification disabled | HAI-managed specification work is blocked. Other agents remain usable. |
| Chronicles disabled | Activity records and lifecycle still work; ordinary transcript recording is disabled. |
| Missing transcript source | Recording verification and enabled-recording closure can be blocked. This does not generally disable the whole Activity-manager. |
| No current Activity, conflicting work, or a closed Activity | Resolve the work boundary or establish a new Activity before substantive work. Closed records still permit attributable supplements. |
| Another specialist wants to invoke an agent | It must return that dependency to Leader; specialists do not delegate. |

These are operation-specific restrictions, not a single global “agent available/unavailable” switch.

**A folder move alone would not implement this redesign.**

The review found concrete coupling:

- Startup hardcodes Environment-manager’s contract and template paths in [startup_check.py](/home/hromar/Desktop/repos/haide/.hai/tools/startup/startup_check.py:19).
- Core conventions link directly to Activity-manager’s contracts.
- Agent-definition-manager currently owns registration; making it optional without another installation path creates a bootstrap problem.
- Specification-manager is more portable, but its registrations and references still require coordinated updates. Its optional configuration flag can remain in core during a minimal extraction.

I would implement the changes in this order:

1. Make Specification-manager an optional package.
2. Separate core registration/validation from optional agent-definition authoring.
3. Make environment procedures callable by Leader.
4. Narrow Activity-manager to continuity, records, and lifecycle.
5. Replace blanket mandatory delegation with delegation justified by the task.
