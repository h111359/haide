## Outcome:

Yes. **Separate permanent machine identifiers from the identifiers shown to the agent.**

For the generated `decisions.md`, use compact numbers:

```markdown
# **--- Part 20260914_0414 ---**

- [I] 1. Use `.aib_product/` for product information.
  Source: `dialog.md:1154`. Replaced by: 2.

- [A] 2. Use `.aih_product/` for product information.
  Source: `dialog.md:2236`. Replaces: 1.
```

The permanent IDs and their mapping to these numbers would live in separate machine-readable files. Scripts handle those files; the agent reads only the compact ledger. Random IDs therefore consume no tokens in the normal decision-reading context.

There are two practical approaches:

| Approach | Benefit | Limitation |
|---|---|---|
| **Sequential display numbers backed by permanent IDs** | Smallest visible identifiers; supports independent extraction and merging. | Numbers may change after merging. References must be resolved against the ledger version the agent read. |
| **Assigned developer prefixes and local counters**, such as `A1`, `A2`, `B1` | Short, stable identifiers without random IDs. | Each writer needs a unique prefix and must preserve its counter. Separate simultaneous writers need separate prefixes. |

**I would use the first approach with the generated-ledger design.** When the agent requests “replace decision 17,” the script resolves `17` using that ledger’s saved mapping. It must reject a stale or mismatched mapping rather than replacing the wrong decision.

If you prefer fewer supporting mechanisms and stable identifiers visible to people, developer prefixes are a simpler compromise.

Each developer gets a unique prefix and maintains a counter across their requests. For example, request `AB7` might introduce decisions `AB21`, `AB22`, and `AB23`. Numbers are never reused.

The merge process would:

1. **Read a pending request and the current shared ledger.**
2. **Compare each proposed decision with existing decisions.**
   - A new independent requirement gets a new merged number.
   - An equivalent requirement maps to the existing number.
   - An explicit replacement invalidates the old decision and adds its replacement.
   - A partial replacement invalidates the whole old decision and adds atomic decisions for the changed and preserved portions.
   - An unresolved conflict becomes a clarification question.
3. **Record the mapping**, such as `AB21 → 37`, in the request’s merge record.
4. **Update the shared ledger** after the affected decisions are resolved.

```markdown
# **--- Part 20260914_0414 ---**

- [I] 36. Use `.aib_product/` for product information.
  Source: `dialog.md:1154`. Replaced by: 37.

- [A] 37. Use `.aih_product/` for product information.
  Source: `dialog.md:2236`.
```
