Presentation preview prepared by Solution-architect on 2026-11-04 for Activity `5f99ff6b-793b-475e-b184-8618582598ef`.

This revision adds phase and action explanations without changing the technical scope; the current plan supplies the technical content, and [requirements.md](requirements.md) supplies the accepted baseline. Current ownership and recording rules remain in force until an authorized implementation changes them. Changes to Solution-architect definitions require the user’s later confirmation of this preview.

Dependencies are prerequisites for phase completion; the early example does not authorize a production switch to the new runtime. Phase 9 depends on all earlier phases, and the graph has no cycles.

**Test and temporary-file placement.** Keep permanent runtime source, contracts, schemas, documentation and maintained test-script source at their planned repository locations. Never create temporary or scratch files inside the repository’s real `.hai/`.

Run every test and place generated fixtures, copied workspaces, outputs, caches, logs, exports, migration rehearsals, backups and journals under `files/test-work/<run-id>/phase-XX/`, relative to the selected Activity folder. In this workspace the Activity folder is `.hai_env/activities/00000000_000000_active/`; a copied test workspace may contain its own `.hai/` inside that Activity folder.

Configure parent and child processes to use working directories and temporary/cache/output settings inside the phase directory. Disable Python bytecode with `-B` or a contained setting; do not assume `-I` honors environment settings. Keep outside-workspace containment fixtures inside the Activity-owned test directory. Verify each affected platform or report the unverified case.

For non-test temporary operations, prefer Activity-local `files/scratch/<operation-id>/` when safe. Check resolved ancestors, links or junctions, ownership and same-filesystem atomic replacement; if unsuitable, use another permitted safe location outside real `.hai/` or stop and report. Never fall back to real `.hai/`. Clean up only identified operation-owned temporary files and preserve failure evidence. Final release, configuration and authorized real-migration locations remain governed by their separate procedures.

The [accepted requirements](#accepted-requirements), [proposed design](#proposed-design-retained-from-the-current-plan) and [remaining technical decisions](#remaining-technical-decisions) are separate in Appendix A. Detailed layouts and file inventories follow the action plan.

## Appendix A — Requirements, proposals and technical decisions

### Accepted requirements

- HAI coordinates work and initializes an absent `.hai_env` without overwriting existing content.
- `.hai` contains a reusable runtime without built-in Leader or Environment-manager definitions.
- Local configuration and agent collections belong in `.hai_env`.
- External agents follow a small integration contract, with Codex supported first and other hosts accommodated by the design.
- Every invocation receives a fresh-context Activity-local notebook, including coordinator runs.
- Prior-run material enters a run only through explicit HAI references.
- Product and specification retain durable knowledge across Activities.
- Agents may directly edit product or specification within their definition and assigned scope.
- Missing token observations remain unknown and never block work.
- Available user/assistant messages are preserved, tool logs remain separate, and transcript synchronization never delays closure.
- Existing environments upgrade only on explicit request while preserving configuration, agents, Activity history and transcript evidence.
- Continuing an Activity in another chat creates a linked coordinator notebook with explicitly selected context.
- Both conflicting contributions remain preserved until affected work is resolved, with only new business choices referred to the user.
- Run all tests and place generated test artifacts under the selected current Activity folder; never place temporary or scratch files in the repository’s real `.hai/`.

The root host conversation executes runtime coordination procedures and receives its own notebook. Domain behavior stays external; the two retired roles are not replaced with differently named built-in agents.

### Activity identity and run boundaries

- Activity UUIDs, record filenames, the sole-current convention and archive naming remain stable.
- Queued work resolves by Activity ID rather than the reusable active-folder path.
- Any location cache remains rebuildable and has no lifecycle authority.
- Run and event schemas receive independent versions without fabricating historical runs.
- Each dispatch, retry or follow-up assignment creates a new run with fresh host context.
- Continuation of an unchanged assignment stays in its run, while a materially changed assignment starts another.
- Ordinary turns continue the coordinator run for the current Activity and chat/session.
- Another chat creates a linked coordinator run, and an Activity switch creates a fresh run.
- Carry-forward references record explicit selection and the referenced revisions.
- Missing session identity uses attributable caller-supplied linkage rather than guessed continuity.

### Run notebook

All paths below are proposed relative to `agent_runs/<run-id>/`.

| Artifact | Content or responsibility |
| --- | --- |
| `run.json` | Identity, links, timestamps, execution state and write scope |
| `assignment.md` | Objective, acceptance, constraints and explicit context |
| `notebook.md` | Decisions, notes, collected information and references |
| `actions.jsonl` | Observed actions, excluding private reasoning |
| `result.md` | Artifacts, checks, dependencies and promotion targets |
| `usage.json` | Observed usage, source, coverage and unavailable values |
| `artifacts/` | Run-specific outputs and evidence |

- Run metadata includes Activity/run IDs, coordinator/agent kind, definition identity/hash and available host/session IDs.
- Metadata preserves attempt, parent and predecessor links alongside timestamps and context references.
- Default files distinguish “not yet recorded” from completion.
- The coordinator owns assignment and lifecycle fields, the executor owns notebook/results, and the adapter owns observed usage.
- Helpers enforce field ownership and expected revisions.
- Notebook content never automatically becomes durable specification.

### External-agent contract

- The contract supplies identity, entry point, scope, execution requirements and assignment/result shape.
- The contract supplies explicit context references, write authority and notebook obligations.
- Native metadata may adapt to the contract without forcing external agents into HAI’s six-heading authoring format.
- Descriptors, wrappers and contained references require validation before selection.
- Creating a descriptor neither registers an agent nor grants permission.
- Optional skills use registered compatible wrappers and the same run machinery.
- Source-library execution and implicit package installation remain disallowed.
- No-settings packages require no values file.

### Small glossary

| Term | Meaning |
| --- | --- |
| Adapter | Code translating an exposed host interface into the runtime contract |
| Durable | Written so supported restart recovery can recover it |
| Idempotent | Safe to repeat without duplicating an already recorded effect |
| Candidate | A preserved proposed file version before publication |
| Compare-and-swap | Publish only when the current file still matches the expected revision |
| Three-way merge | Reconcile two contributions against their shared base version |
| Outbox | Durable queue of captured events awaiting verified delivery |

### Migration preservation checklist

- [ ] Specification and Git owner settings retain their values and provenance.
- [ ] Chronicles enablement/threshold, model profiles and unknown fields remain preserved.
- [ ] Local package differences remain reviewed and recoverable.
- [ ] Unmapped retired-role settings remain archived, inventoried and inactive.
- [ ] Activity IDs, original inputs, revision history and timestamps remain preserved.
- [ ] Original implementation-start markers and archived paths retain their meaning.
- [ ] Exact transcript bytes, checkpoints and required legacy readers remain available.
- [ ] Any transcript conversion remains separately attributable.
- [ ] Legacy work gains no fabricated runs, host IDs or usage.
- [ ] New runs begin at cutover.

### Release preservation checklist

- [ ] The exact-commit export includes reusable `.hai`, the license and required documentation.
- [ ] The export excludes `.hai_env`, `.hai/agents`, credentials, histories and the source library.
- [ ] Candidate identity and compatibility claims match verified contents.
- [ ] The recorded 0.2.0 candidate remains historical evidence.
- [ ] Selected environments retain compatible recovery snapshots and migration journals.
- [ ] Recovery preserves newer edits instead of automatically rolling them back.

### Existing test suites

These suites are implementation verification tasks; they were not run for this plan revision. Keep the test scripts at their planned repository paths, but run every test from the selected Activity folder.

Put fixtures, copied workspaces, generated outputs, caches, logs and exports under `files/test-work/<run-id>/phase-XX/`. Configure parent and child subprocess working directories and temporary/cache/output paths there. Disable Python bytecode with `-B` or a contained setting; do not assume `-I` honors environment settings. Keep outside-workspace containment fixtures inside the Activity-owned directory. Verify each affected platform or report the unresolved case. Tests cannot control host-internal files inaccessible to the code.
