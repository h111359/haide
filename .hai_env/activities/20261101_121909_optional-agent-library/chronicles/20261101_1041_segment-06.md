**The library should be a source collection, not another executable agent registry.**

The intended relationship should be:

```text
hai_agents_library → explicit installation/update → .hai_env/agents
                                                    ↓
                                            workspace catalogue
                                                    ↓
                                                execution
```

Startup should continue discovering executable agents only through the existing core and workspace catalogues. A package’s presence in the library must not make it selectable, registered, or enabled.

There are two complementary authorities:

- **Library copy:** authoritative for shared package development.
- **Installed copy:** authoritative for what a particular workspace currently executes.

Editing the library must not silently alter installed behavior. Conversely, editing an installed copy must not silently change the golden source.

I recommend this source layout:

```text
hai_agents_library/
  README.md
  agents/
    agent-definition-manager/
    specification-manager/
    git-manager/
    release-manager/
```

Each folder should contain the **complete package**—definition, procedures, concepts, conventions, scripts, tests, and contracts—not just `SKILL.md`.

The extra `agents/` level matches the installed directory depth, which helps with existing relative paths. Nevertheless, verification should test the actual installed layout rather than rely on matching depth alone.

**Several concrete changes are required beyond copying the folders.**

| Area | Impact |
|---|---|
| **Registration** | Remove the two outgoing core registrations and register their installed workspace copies. Leaving both runtime definitions creates name collisions. The library itself must not participate in runtime collision checking. |
| **Agent-definition-manager ownership** | Its procedures currently recognize only framework and workspace definitions. It needs an explicit distinction between maintaining a library source package and modifying an installed agent. |
| **Bootstrap installation** | A fresh workspace cannot invoke an unregistered library copy of Agent-definition-manager to install itself. A human procedure or narrow core installation mechanism must handle the first installation. |
| **References and helpers** | Core-relative references need updating to installed core or peer packages. Installed files must never resolve missing resources by falling back to the library. |
| **Optional dependencies** | Core documentation currently links directly to Specification-manager. Core must remain understandable and usable when that optional package is absent. |
| **Validation** | Existing agent validation accepts canonical core/workspace locations, not arbitrary library paths. Initially, source packages can be validated by staging them into a temporary installed layout. |
| **Release packaging** | The current bundle allowlist includes `.hai` and selected documentation, not the proposed library. Without a deliberate packaging change, the moved agents disappear from distributed bundles. |
| **Release contracts** | Release-manager currently references Specification-manager’s contract under `.hai`. Its runtime peer references and candidate-source inspection paths need distinct treatment. |
| **Installation documentation** | “Replace `.hai` to upgrade” will no longer upgrade these installed agents. Optional-agent installation and updates need separate instructions. |

These changes **do not inherently require changing the environment state format or specification data format**. Nor do they require refactoring Leader, Environment-manager, or Activity-manager in this step.

**The four packages differ in portability.**

- **Specification-manager** is the strongest portable package. It already supports standalone use and carries its own specification contract. Installing it should not automatically enable specification management or create a specification tree.
- **Agent-definition-manager** is reusable HAI administration tooling. It depends on core conventions and validation tools, and needs the source-maintenance and bootstrap changes described above.
- **Git-manager** is reusable across compatible HAI workspaces, but is not standalone. It depends on HAI configuration, integration settings, Activity context, and recording requirements. Its helper also assumes the installed directory layout. Copying the package must not copy credentials or enable integrations.
- **Release-manager** is currently a **HAI bundle release manager**, not a generic product-release agent. It contains HAI-specific archive names, manifest paths, compatibility checks, and version policy. It can belong in the library, but should be labelled accurately. Generalizing it would be a separate task.

“Installable in any compatible workspace” therefore does not mean “appropriate for every workspace.”

**The main disadvantages are manageable, but real.**

1. **Installed copies become stale.** A library fix does not reach workspaces until they update.
2. **Local edits create upgrade conflicts.** Blind copying can destroy customization; copying over an existing folder can also leave obsolete files behind.
3. **This repository will contain duplicate maintenance surfaces.** A library-only change does not update the locally running agent. An installed-only change does not improve the golden source.
4. **Compatibility becomes more visible.** Agent format, core helpers, model requirements, peer dependencies, and package-specific data contracts can change independently.
5. **Optional Agent-definition-manager complicates recovery.** It cannot be relied on before installation and registration. Invalid environment state can also prevent using workspace registrations, while core diagnostic tools remain available.
6. **Distribution needs a clear policy.** Shipping the library with HAI is simple but retains optional source bytes in every bundle. Distributing it separately adds acquisition and version-matching work.

There is also a boundary in your “no direct references” requirement that needs clarification: installation, source maintenance, and release packaging necessarily read library files. That is different from an installed agent loading its operational instructions or helpers from the library.

**I recommend a deliberately small first version.**

| Decision | Recommended first version |
|---|---|
| Distribution | Ship core plus the library in one HAI bundle; library packages remain uninstalled until selected. |
| Version tracking | Use the library/repository revision initially, plus an installed baseline identifier or digest. Independent package versions can come later. |
| Shared changes | Edit the golden source, then explicitly update selected installations. |
| Local customization | Preserve it; stop an update when installed files differ from their baseline and require an explicit merge/replace decision. |
| Updates | Replace a validated whole-package candidate, preserving a recoverable previous copy. Avoid overlay copying that leaves removed files behind. |
| First installation | Document a human bootstrap procedure using core validation tools. Add an installer helper later if repeated installation justifies it. |
| Runtime isolation | Verify in a temporary fixture that installed agents still work when the library is absent. |

This avoids building a package manager before one is needed.
