## What

Give every sub-agent invocation its own working folder inside the current Activity.
Provide that folder to the invoked agent as its space for temporary files, log
files, explanations of its work and other invocation-specific supporting material.

Folders are distinct per invocation, not just per agent name. If the same agent
is spawned multiple times in the same Activity, each invocation receives a
different folder and retains its own files.

## Why

Keep each invocation's working material separate and attributable, so repeated
or concurrent agent invocations do not mix their temporary files, logs or work
explanations. Keep that material associated with the Activity in which the
invocation took place.

## Acceptance Criteria

1. Every sub-agent invocation assigned to an Activity receives a dedicated working
   folder inside that Activity, with its location supplied to the invoked agent.
2. Different invocations have different folder paths, including multiple
   invocations of the same agent within one Activity.
3. Each invocation can store its temporary files, logs and explanations in its
   assigned folder without sharing that folder with another invocation.
4. A new invocation does not overwrite or reuse an earlier invocation's working
   folder or files.
5. Invocations in a different Activity receive folders under that Activity rather
   than reusing the previous Activity's folders.

## Implementation

Implemented `activity invocation-allocate`, with unique Activity-local folders,
allocation metadata, preview/apply behavior, exclusive creation and partial-failure
reporting. The [invocation contract](../../.hai/conventions/agent-invocation_conv.md)
and [runtime guide](../../.hai/tools/runtime/README.md) define host handoff and use.

Each new spawn receives a fresh allocation. Same-live-instance follow-ups retain
the folder; failed/not-dispatched allocations are retained. Host closure waits for
actual ended-writer evidence; allocation alone does not launch or stop agents.

Verification on Linux/Python 3.12.3: all 14 allocation fixtures passed; core suites
ran 205 tests, with 203 passed and two Windows-only skips. Three real QA probes in
controlled test Activities verified concurrent same-role folders, separate files,
a same-instance continuation, preserved archival bytes, stale-ID rejection and a
fresh Activity handoff. A fourth QA invocation used its allocated folder in this
product Activity and independently found no high/medium issues.

Same-account filesystem access is not OS isolation. Real indeterminate launches
were not induced; controlled no-dispatch and fixture failure cases are identified
as such. Windows/macOS execution remains unverified. The implementation is ready
for acceptance; no feature-completion decision or commit is inferred.

## Resolution

Completed with explicit user acceptance (“complet4e, commit, close activity and
open a new one”) after the implementation report and independent QA review.

- AC1: actual assigned QA agents received existing runtime allocations and verified
  matching Activity/invocation manifests before writing their supporting files.
- AC2: two overlapping invocations of quality-assurance received distinct folders;
  repeated/new spawns received fresh allocations, while a same-live-instance
  follow-up retained its existing folder under the accepted implementation plan.
- AC3: real invocations wrote separate sentinel, report and work-note files only
  within their supplied folders.
- AC4: earlier bytes survived later allocations, follow-up and archival unchanged;
  collisions and partial failures were covered by focused runtime fixtures.
- AC5: a later test Activity received a new allocation and a real agent handoff;
  stale prior Activity IDs were rejected, and archived files remained unchanged.

All 14 new allocation tests passed. Core suites: 205 run, 203 passed and two
Windows-only skips on Linux/Python 3.12.3. Independent final QA found no high/medium
issues and verified ten archive hashes. Detailed reports are retained by the
linked Activity. Real uncertain host launches were not induced; controlled
no-dispatch and injected failures are distinguished from real launch evidence.
Host writer coordination is not OS isolation or enforcement of external process
lifetime by direct close commands. These reported limits were included before
acceptance. No automatic cleanup, runtime spawn engine or state migration is added.
