In `definitions/convention_prompt_format.md` is written "Template placeholders are not defaults or valid submissions, even if a field's schema would otherwise allow such a value. ## Outcome:

The rule aims to prevent **an unfinished template from accidentally becoming an executable request**. That is useful, but its current representation has an ambiguity.

Small correction: the [current file](/home/hromar/Desktop/repos/haide/definitions/convention_prompt_format.md:98) says optional parameters **SHOULD** be omitted, rather than **MUST**.

The rule distinguishes three things:

- **Placeholder:** “The caller still needs to choose.”
- **Default:** “Use this value if the caller omits the parameter.”
- **Explicit value:** “The caller chose this value.”

For example:

```yaml
inputs:
  source_files: []   # Required placeholder
```

An empty list might satisfy the schema, yet executing with it could produce an empty result simply because the caller forgot to fill it in. The rule tells the executor not to mistake that oversight for a deliberate choice.

Omitting unchosen optional parameters serves a related purpose. Suppose an optional `language` defaults to `"en"`. Leaving it out allows that default to apply; supplying `language: ""` supplies a different value, which might be invalid or mean something else. This also keeps defaults defined in one place—the schema.

**The weakness is that intention is not observable from the value alone.** An untouched `[]` and an intentionally supplied `[]` look identical. A YAML parser cannot distinguish them, and an agent may need clarification. The wording “or intentionally supply” permits legitimate empty values, but does not define how callers communicate that intention.

There are several alternatives:

| Approach | Benefit | Tradeoff |
|---|---|---|
| **Accept every schema-valid submitted value** | Simple, deterministic; submitting means accepting the values | Forgotten placeholders can execute |
| **Use explicit markers**, such as `"<REQUIRED>"`, and reject unresolved markers before schema validation | Missing choices are visible and detectable | Needs a reserved marker convention; templates may contain values of the wrong type |
| **Omit unfilled fields**, listing required fields in comments or documentation | Standard required-field validation detects missing inputs | Less convenient to fill by copying |
| **Track “unset” separately in a form or invocation builder** | Distinguishes unset from deliberate `""`, `[]`, `false`, or `0` | Requires tooling |
| **Provide runnable examples with realistic values** | Convenient starting point | Users may accidentally execute example values; examples need clear labeling |

For this copy-and-paste prompt format, I would favor **explicit required-value markers plus omission of unchosen optional parameters**. It preserves the benefit while making unfinished inputs recognizable.

If simplicity is the priority, accepting all schema-valid values is also a coherent choice. In that design, submitting the invocation counts as choosing its contents, and constraints such as `minLength: 1` or `minItems: 1` should reject empty values only when the task actually requires nonempty input.

## Prompt:

I want the template to demonstrate all the possible parameters. Also there to be a hint if the parameter is required or optional. Also I need it to be easy for fulfillment. Suggent me a solution.


## Outcome:

I suggest **showing every parameter, with a short inline comment and an explicit “fill me in” marker**:

```yaml
invocation:
  instruction: >
    Execute the instructions in the file named by prompt using the inputs
    below. Treat "<REQUIRED>" as unfilled and ask for its replacement.
    Treat "<OPTIONAL>" as omitted. Validate all remaining values against
    the input schema before proceeding.
  prompt: "definitions/example.md"
  inputs:
    source_files: "<REQUIRED>" # Required · array of paths · e.g. ["notes.md"]
    destination: "<REQUIRED>" # Required · directory path · e.g. "output/"
    language: "<OPTIONAL>"    # Optional · string · default: "en"
    max_items: "<OPTIONAL>"   # Optional · integer · e.g. 20
    overwrite: "<OPTIONAL>"   # Optional · boolean · default: false
```

To fill it in, the caller replaces required markers and any optional markers they want to choose. They can leave the other optional markers untouched—no need to delete lines.

This gives you:

- **Discoverability:** every accepted parameter appears.
- **Visible guidance:** comments show requiredness, expected type, and an example or default.
- **Unambiguous empty values:** `""`, `[]`, `false`, and `0` are actual supplied values, subject to the schema.
- **Easy completion:** only required markers must be replaced.

The convention should explicitly define these markers as **reserved template syntax processed before schema validation**. For example, replacing `"<REQUIRED>"` with `["notes.md"]` supplies an array, despite the original marker being a string.

I would replace the quoted paragraph with:

> The invocation template MUST show every declared parameter. Each parameter MUST have an inline comment identifying it as required or optional and providing concise filling guidance consistent with its schema. Unfilled required parameters MUST use the reserved marker `"<REQUIRED>"`; unchosen optional parameters MUST use `"<OPTIONAL>"`. Before input validation, optional parameters containing `"<OPTIONAL>"` MUST be treated as omitted, allowing declared defaults or omission behavior to apply. Required parameters containing `"<REQUIRED>"` MUST trigger a request for completion. All other supplied values MUST be validated normally, including empty strings, empty collections, zero, and false.

For chat execution, the standard invocation instruction can carry these rules. Any future programmatic runner would need to implement the same marker handling.
