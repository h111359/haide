## Outcome:

**I’d use chat as the interface, backed by a small, reusable “explain an entry” convention in AIH.** You should be able to say “Explain entry 3” while reading a file, and have the framework supply the relevant context automatically.

Your current extraction format already provides the foundation: numbered entries, source citations, and links between related findings.

Three reasonable options:

| Option | How it works | Tradeoff |
|---|---|---|
| **Ask directly in chat** | Identify the file and entry, then ask for an explanation. | Available immediately; you must provide enough context to identify the entry. |
| **Reusable explanation prompt** | Add a companion such as `definitions/explain_context.md`, accepting a file, entry ID, and optional question. | Consistent answers across chats and agents with little extra machinery. |
| **“Explain” action in AIH** | Select an entry in the document viewer and open a contextual question in **Ask a question**. | Most convenient for regular use; requires interface integration. |

**My recommendation: start with the reusable prompt, then connect it to AIH’s existing question workflow.** AIH already documents an independent, read-only Q&A lane in its [user guide](/home/hromar/Desktop/repos/haide/.aih/USER_GUIDE.md:27), so this can extend an existing mechanism.

The explanation convention should tell the agent to:

- Read the selected entry, its cited source **with surrounding context**, and relevant linked entries.
- Explain its meaning in plain language, including scope and conditions.
- Give a concrete example, clearly marked as illustrative.
- Explain the reason only when the sources support it; identify anything unknown.
- Answer follow-up questions without changing the definitions.

For example, you could ask today:

> In `definitions/definitions_R20260925_2309/requirements.md`, explain entry 3 in plain language. Read its cited source and surrounding context. Give a practical example, distinguish source-supported meaning from illustration, and leave the files unchanged.

For your actual entry 3, a suitable explanation would be:

> Before installing or building AIH, the agent must inspect the existing workspace and any applicable instructions. It must preserve the product content already present.
>
> For example, if the folder already contains application code and project instructions, installation should accommodate those files and follow the instructions. This example illustrates the requirement; it does not add a new installation rule.
>
> The cited source states this obligation directly but does not specify a particular backup or installation technique.

Two design details matter here.

**Bind the question to the document version.** Your [extraction contract](/home/hromar/Desktop/repos/haide/definitions/extract_context.md) explicitly allows entry numbers to change on regeneration. AIH should retain the file path, entry number, quoted entry text, and snapshot fingerprint with the question. An old discussion about “entry 3” must not silently attach to a different entry later.

**Keep explanation separate from changing the definition.** “What does this mean?” produces an answer. “This should mean something else” should become an explicit correction or clarification captured as source material for the next extraction. Saving explanations directly inside the generated folder would be fragile because extraction replaces that entire folder.

The intended experience is simple: **select an entry → Explain → ask follow-ups → optionally record a correction.** Chat supplies the conversation; AIH supplies precise context, source grounding, and continuity.

## Prompt:

What do you think about the idea of every prompt to have a yaml header in which the prompt is summarized? Plus there is a form which needs to be fulfilled and This to be the format of invocation of this prompt. In the prompts `definitions/extract_context.md`, `definitions/merge_context.md` and `definitions/explain_context.md` there are example invocations. ## Outcome:

Yes—I think this is a good direction. **A YAML header can make each prompt both readable by a person and usable by the web application.** It would define the prompt’s purpose, required inputs, and expected output; the Markdown body would retain the detailed execution instructions.

I would make the header the **authoritative definition of the input form**, so you do not have to maintain the same parameter definitions separately in the prompt, invocation example, and web application.

For `explain_context.md`, a proposed format could be:

```yaml
---
schema_version: 1
id: explain_context
title: Explain a definition entry
summary: >
  Explain a numbered definition entry using its sources,
  related entries, and practical examples.

inputs:
  file:
    type: string
    required: true
    label: Definitions file
    description: Path to the file containing the entry.
    ui:
      widget: file-path

  entry:
    type: integer
    required: true
    minimum: 1
    label: Entry number
    description: The explicit numeric ID, not the line number.

  question:
    type: string
    required: false
    label: Specific question
    description: An optional aspect you want explained.
    ui:
      widget: textarea

output:
  channel: chat
  format: markdown

effects:
  files: read-only
---
```

These would be conventions we define for AIH; the application would need support for interpreting them.

The web application could use this header to:

- Display the prompt’s title and summary in a prompt catalog.
- Generate fields, help text, and required-field indicators.
- Validate basic values before submission.
- Produce a consistent invocation.
- Show whether the prompt answers in chat or writes files.

**Keep the prompt definition and a completed invocation separate.** The header describes the blank form. Submitting the form supplies its values, for example:

```yaml
prompt: definitions/explain_context.md
inputs:
  file: definitions/definitions_R20260925_2309/requirements.md
  entry: 3
  question: What does preserving existing product content mean?
```

The same invocation could be pasted into chat or generated by the application. A runner would load the referenced prompt and pass these values with its instructions.

For your three prompts, the mapping is straightforward:

| Prompt | Required fields | Optional fields | Result |
|---|---|---|---|
| `extract_context` | `sources`, `request_id`, `destination` | None currently | Generated request folder and chat summary |
| `merge_context` | `request_folder`, `product_folder` | None currently | Updated product definitions and chat summary |
| `explain_context` | `file`, `entry` | `question` | Explanation in chat |

A few conventions would make this reliable:

1. **Separate field validation from execution checks.** YAML can define “positive integer” or “nonempty list.” The prompt or runner must still check whether files are readable, the entry exists, or a merge has unresolved issues.

2. **Resolve relative paths consistently.** I suggest resolving invocation paths against the selected workspace root. Source citations inside a definitions file would continue to resolve relative to that file.

3. **Do not treat examples as defaults.** Your extraction and merge prompts deliberately require explicit paths and identifiers. Generated forms should preserve that behavior.

4. **Keep complex rules in the Markdown body.** Independent review, source interpretation, conflict handling, and safe replacement belong in the execution instructions. The header should stay compact.

5. **Reject contradictions.** If the header and body disagree about required inputs or output behavior, report a prompt-definition error instead of guessing.

I would adopt this for **reusable, invocable prompts**, starting with these three. The first useful step is a shared header specification and matching headers; automatic form generation can then build on that contract without changing how the prompts work in chat.
