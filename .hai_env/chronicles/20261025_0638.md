## Prompt:
Educate me more. Tell me about the idea of releases and the relation to commits and relation to tagging in GitHub of the releases. I need to understand these concepts.


## Outcome:
A **release is a selected, named version of your product that you make available for people to use**. Commits preserve the development history; tags identify the exact point you released; GitHub releases provide the publication and downloads.

There are four concepts to distinguish:

| Concept | What it represents | Example |
|---|---|---|
| **Commit** | A saved snapshot of the repository, with history and a unique identifier | `a83f921…` |
| **Branch** | A name tracking a line of development | `main` |
| **Tag** | A name identifying a particular point in history | `v0.1.0` |
| **GitHub release** | A publication associated with a tag, with notes and downloads | “HAI 0.1.0 — First preview” |

**A commit records your work.**

Suppose you make these commits:

```text
A: Add specification conventions
B: Improve startup validation
C: Prepare installation instructions
```

The history looks like this:

```text
A ── B ── C
          ↑
         main
```

Each commit identifies the repository’s tracked contents at that point—not just the changed file. Git can show the differences between commits and recover an earlier snapshot.

You might make dozens of commits while preparing one release. **A commit does not automatically become a release.** It can contain an intermediate step that you are not ready to distribute.

**A branch moves as development continues.**

`main` currently points to C. When you add commit D on that branch, `main` advances to D.

That makes `main` useful for following current development, but unsuitable as a permanent identifier for a published version: downloading `main` today and next week can give different contents.

**A tag gives a particular commit a recognizable name.**

When C is ready for distribution, you can attach the tag `v0.1.0` to it. Later, after more development:

```text
A ── B ── C ── D ── E
          ↑         ↑
       v0.1.0      main
```

The tag still identifies C. Someone choosing `v0.1.0` gets the released state, while someone choosing `main` gets the newer development state.

Tags are a Git feature; they exist independently of GitHub. Git supports *annotated tags*, which include a message, author information, and date. Those are a good fit for releases. [Git tagging documentation](https://git-scm.com/book/en/v2/Git-Basics-Tagging)

A tag can technically be moved or deleted, but **you should treat published release tags as permanent**. If you discover a mistake, publish a new version rather than change what an existing version means.

**A GitHub release publishes the tagged version for users.**

The tag identifies the source. The GitHub release adds the user-facing information:

- What changed.
- Who should upgrade.
- Compatibility and migration instructions.
- Downloadable packages.

GitHub releases are associated with tags. You can have a tag without a release page. GitHub also provides source ZIP and tar downloads for the tagged repository snapshot, and you can attach separately prepared packages. [GitHub release documentation](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)

For HAI, this distinction matters:

- The automatic **source archive** contains the repository snapshot.
- A prepared **`hai-0.1.0.zip`** could contain only the intended distributable framework files.

That lets your development repository contain tests, working material, or other resources without requiring all of them in the installation package.

**Here is what your first HAI release could look like.**

1. Develop and test on `main` as you do now.
2. Decide that the current work is ready for an experimental release.
3. Set the proposed `.hai/release.json` to `0.1.0`, write release notes, and commit those changes.
4. Verify that exact commit.
5. Create the tag `v0.1.0` pointing to it and publish the tag to GitHub.
6. Create a GitHub release associated with `v0.1.0`, attach the installation package, and publish it.
7. Continue developing on `main`.

You do **not** need a separate branch for each release. Branches become useful later if, for example, you need to maintain an older version while developing the next one.

Suppose someone finds a bug after publication. You fix it in another commit, prepare version `0.1.1`, tag its verified commit, and publish another release:

```text
A ── B ── C ── D ── E ── F
          ↑         ↑     ↑
       v0.1.0    v0.1.1  main
```

Users can still obtain either published version.

Finally, the three version identifiers we discussed have complementary purposes:

| Identifier | Purpose |
|---|---|
| `.hai/release.json`: `0.1.0` | Lets the installed files identify their version |
| Git tag: `v0.1.0` | Identifies the corresponding source commit |
| GitHub release: “HAI 0.1.0” | Presents that version and its downloads to users |

Git does not choose or increment these numbers for you. **You decide when to release and which version number the changes warrant.** Automation can then check that the manifest, tag, and package agree.

**2. Configure GitHub Actions once**

GitHub Actions runs commands on a machine provided for the workflow. Its instructions live in a YAML file inside your repository.

The release workflow’s trigger would look like this:

```yaml
name: Release HAI

on:
  push:
    tags:
      - "v*"
```

This means: run when a tag whose name starts with `v` is pushed. Ordinary commits to `main` do not trigger this particular workflow. GitHub supports filtering push events by tags. The complete workflow would perform these steps, in order:

1. Obtain the source from the **exact tagged commit**.
2. Validate the version number.
3. Check that `v0.1.0` matches `"version": "0.1.0"` in the manifest.
4. Check agreement between the release manifest and agent contract declarations.
5. Run HAI’s required validation and tests.
6. Build the ZIP from the intended framework files.
7. Inspect the package contents.
8. Create the GitHub release and upload the ZIP.

**If validation fails, publication stops.** Matching `v*` only starts the workflow; it does not prove the tag is a valid release version.

The publishing job needs `contents: write` permission. It can authenticate using GitHub’s automatic workflow token:

```yaml
permissions:
  contents: write

env:
  GH_TOKEN: ${{ github.token }}
```

You normally do not need to create and store a personal access token for publishing a release in that same repository. Repository or organization policy must permit the workflow’s requested access. [Workflow authentication](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token)


This assumes your implementation changes and the one-time workflow setup have already been committed.

Before tagging, inspect:

```bash

git log -1 --oneline
```

You want a clean working tree and the intended, verified commit.

**A tag identifies committed content. Uncommitted edits will not be included in the release.**


**With the proposed automation, pushing that tag is your instruction to publish once checks pass.**

There is no need to open GitHub and manually create the release. The tag push starts the workflow.

This packages `.hai/` from the tagged snapshot. It excludes `.hai_env/` and other repository paths. It also avoids accidentally including uncommitted local files. Git’s archive command supports selecting a revision and limiting the included paths. [Git archive documentation](https://git-scm.com/docs/git-archive)

For the final implementation, we would define the package contents deliberately—including any required license or installation documents outside `.hai/`.

Inside Actions, `dist/` exists on the workflow machine. The ZIP must be uploaded as a release asset to become the user-facing download.

**6. Automation publishes using GitHub CLI**

The publishing command would have this form:

```bash

  --verify-tag \
  --title "HAI 0.1.0" \

```

Here:

- `v0.1.0` selects the release tag.
- The ZIP argument uploads the package.
- `--verify-tag` requires the tag to exist remotely.
- `--title` sets the display title.
- `--notes-file` uses your prepared release notes.

Without `--verify-tag`, the CLI can create a missing tag automatically from the default branch. Requiring an existing tag makes the release process more explicit. [GitHub CLI release creation](https://cli.github.com/manual/gh_release_create)

The automation would derive these filenames and values from the validated version, rather than hardcoding `0.1.0`.

```bash

```

```bash

```

`gh run watch` lets you follow a workflow run until it completes. [CLI workflow monitoring](https://cli.github.com/manual/gh_run_watch)

**8. Choose whether publication is automatic or staged**

There are two useful operating modes:

| Mode | What happens after a successful tag-triggered workflow |
|---|---|
| Automatic publication | The release becomes available immediately |
| Draft release | The package and notes are prepared, but publication waits |

For drafts, add `--draft` to the creation command. You can subsequently publish from the CLI, so staging does not require the web interface. Release candidates such as `1.0.0-rc.1` can be marked with `--prerelease`. [Release creation options](https://cli.github.com/manual/gh_release_create)

For HAI, automatic publication after verification is a reasonable target. A draft is useful while establishing and checking the first release process.
