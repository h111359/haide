# Proposed implementation plan: HAI runtime and Activity runs

Prepared by Solution-architect on 2026-11-04 for Activity `5f99ff6b-793b-475e-b184-8618582598ef`.

This is a design recommendation grounded in the accepted requirements and current repository. It authorizes no implementation, environment upgrade, package replacement, release, or Activity closure. Current ownership and recording rules continue until an authorized implementation changes them. Requirements/acceptance references below mean items 1–11 in this Activity’s `requirements.md`.

## Architecture and compatibility direction

Make `.hai` the reusable coordination protocol plus deterministic Python tools. Move coordination, environment administration, Activity lifecycle, installation, and run recording into runtime procedures; keep domain behavior in external agents. Do not replace Leader/Environment-manager with differently named built-in agents. The host’s root conversation executes the coordinator procedure and receives its own run notebook.

Recommended canonical families:

| Location | Responsibility |
| --- | --- |
| `.hai/start.md`, `procedures/` | Bootstrap, coordinate, dispatch, reconcile, close/supplement, install/register, explicitly migrate. |
| `.hai/concepts/`, `conventions/`, `contracts/`, `schemas/`, `templates/` | Runtime meanings, integration contracts, versioned validators and structural templates; no selected workspace policy. |
| `.hai/tools/{startup,configuration,agents,activities,runs,transcripts,migrations}/` | Standard-library validation, safe mutations, durable capture and recovery. |
| `.hai/adapters/codex/` | Codex capability/source normalization boundary; optional future host adapters use the same contract. |
| `.hai_env/state.json`, `config/runtime.json`, `model_profiles.json`, `agent_instructions.md` | Format identity, selected runtime policy, local model mappings and fixed instructions. |
| `.hai_env/agents/`, `config/agents/` | Installed external packages/catalogue and their separately preserved settings. |
| Configured Activity store | Existing records plus `agent_runs/<run-id>/`, transcript events and rendered views. |
| `.hai_env/runtime/` | Recoverable operation journals, capture outbox, locks and migration evidence; no canonical product knowledge. |

Recommend environment format 4, subject to implementation-time version confirmation: move selected Activity/recording policy from format-3 state into `config/runtime.json`; retain unknown fields losslessly. Materialize selected runtime values during initialization/migration, rather than treating runtime templates or Python constants as hidden policy. Document safe bootstrap choices in the environment initializer; do not silently activate recording, specification, Git or other optional capabilities. Preserve existing agent configuration contracts/default semantics independently. Product/specification locations remain their existing canonical locations, with all selected paths/settings in `.hai_env`.

Keep UUID Activity identity, existing record filenames, sole-current convention and archival naming. Resolve queued work by Activity ID, never the reusable active-folder path. An optional location cache is rebuildable and never a second lifecycle authority. Introduce explicit independent run/event schema versions; legacy records remain readable without retrospective run fabrication.

Each run gets `run.json`, `assignment.md`, `notebook.md`, `actions.jsonl`, `result.md`, `usage.json`, and `artifacts/`. The notebook has decisions, notes, collected information and references; default files explicitly distinguish “not yet recorded” from completion. Metadata includes Activity/run identity, coordinator/agent kind, agent definition identity/hash, host/session identifiers when exposed, attempt/parent/predecessor links, timestamps, execution state, context references and assigned write scope. Coordinator owns assignments/lifecycle, executor owns notebook/results, adapter owns observed usage; helpers enforce field ownership and revision checks. Actions record observable operations, not private reasoning.

A dispatch, retry or follow-up assignment creates a new run and fresh host context. Continuation needed to finish one unchanged assignment remains that run; a materially changed assignment starts another. Use one coordinator run per Activity per host chat/session; ordinary turns continue it, another chat creates a linked run, and an Activity switch creates a fresh run. Record explicit carry-forward references and their revisions. Session identity unavailable means caller-supplied linkage with provenance, not guessed continuity.

The minimal integration contract supplies identity/entry point, scope, execution requirements, assignment/result shape, explicit context references, write authority, and notebook obligations. Recommend a small `hai.json` package descriptor and catalogue support alongside existing native `SKILL.md` entries. Do not require arbitrary external agents to adopt HAI’s six-heading authoring format. Existing native metadata can adapt to the same contract. Validate wrappers/descriptors and their contained references before selection; creating one neither registers its agent nor grants permission. Optional skills execute through a registered compatible wrapper and identical run machinery; no source-library execution or implicit installation. No-settings packages need no values file.

## Phased delivery

### 1. Establish contracts and prove host capabilities

Create runtime contract/design fixtures and an old-to-new responsibility/path matrix. Trace `.hai/start.md`, core role procedures, state/activity/agent/model conventions and their Python consumers before moving them. Define capability results for fresh dispatch, model/effort control, session identity, message source, delivery notification, usage, cancellation and file isolation. Report supported/unsupported/unknown separately.

Perform a small Codex integration spike using only actually exposed interfaces. The current spawn surface advertises `fork_turns="none"`; prove fresh assignment construction, without equating empty history with filesystem isolation. Probe transcript/usage availability without searching arbitrary host histories. This chat has no identified authoritative JSONL source. Test explicit export/import fallback and document unsupported post-delivery hooks rather than inventing them.

Exit: versioned contracts, host capability evidence, ownership matrix and an implementable Codex dispatch/capture strategy; gaps have concrete supported fallbacks or block only the unsupported claim. Prerequisite for every later phase.

### 2. Build the first working vertical slice

Add safe run allocation and bootstrap tools under `.hai/tools/runs/` and runtime procedures in a disposable workspace. Initialize an absent environment without overwriting existing files; discover/create an Activity; allocate its coordinator notebook; dispatch one external no-settings agent with fresh context; record result, observed actions and unavailable usage. Finish an analysis-only Activity without any transcript dependency.

Persist run allocation before dispatch; use a dispatch operation ID and host receipt where available. A crash after an uncertain dispatch must produce “dispatch unknown” for reconciliation, never silently spawn a duplicate. A definite failed attempt remains recorded; authorized retry creates a linked run. Do not introduce a mandatory server/database for this slice.

Exit: an end-to-end fixture plus one controlled Codex demonstration proves requirements 2–5 and 7 with a minimal external agent. Existing runtime remains usable; no in-place production cutover yet.

### 3. Extract runtime coordination and environment services

Move reusable resources from `.hai/agents/environment-manager/{concepts,conventions,procedures,templates}` and Leader procedures into the new canonical families. Update `startup_check.py`’s role-owned `TEMPLATE`/`CONTRACT` constants, `configuration_tools.py`, `agent_tools.py`, and startup/format documentation together. Add explicit mutation operations rather than making the currently read-only helpers write during validation.

Keep missing/unreadable instructions, invalid state, bad aliases, incompatible profiles, and malformed catalogues distinguishable from absence. Scope failures to dependent operations. Runtime configuration cannot grant task permission. Bootstrap and first-package installation must work with no optional agent or source library. Separate runtime procedures from agent procedure authoring rules so the extracted resources need no fictitious role owner.

Exit: core-only temporary workspaces initialize, validate, discover and administer Activities without selecting either old role; read-only commands remain nonmutating. Depends on phases 1–2.

### 4. Complete dispatch, notebooks and external-agent integration

Implement descriptor/catalogue validation, selected-package configuration, explicit context manifests, lifecycle reconciliation and result acceptance. Preserve native catalogue rows and selection descriptions through an explicit compatibility adapter or reviewed migration; do not silently reinterpret arbitrary definition files. Resolve models against current host capabilities without substitutions.

Record failed/cancelled/interrupted runs and output provenance. Usage fields carry observed/partial/unavailable status, source, coverage and null unknown values. Deduplicate source event IDs, distinguish cumulative counters from deltas, and avoid counting coordinator/child totals twice. Results include produced artifacts, checks, unresolved dependencies and promotion targets; notebook content never automatically becomes durable specification.

Exit: dispatch/retry/follow-up produce distinct linked runs; new-chat continuation creates the linked coordinator run; two different agent collections and a wrapped optional skill work with identical core bytes. Explicit prior-reference and denied implicit-context tests pass. Depends on phase 3.

### 5. Implement safe shared writes and conflict resolution

Add a small mutation service with exclusive create, path/alias checks, expected revisions, temporary writes, durable operation journals and short publication locks. A filesystem rename is not a multi-file transaction: expose interrupted operations and deterministic recovery steps. Keep separate locks for Activity metadata, per-run output and transcript reconciliation.

For product/specification edits, capture base hashes and each contribution before publication. Prefer scoped worktrees/candidate copies for overlapping work; allow direct domain editing within the assigned checkout and publish through compare-and-swap. For a shared canonical editor, require the protocol’s preimage/candidate capture and checked publish. On conflict, retain both candidates and base, record a conflict object, and reconcile through a three-way merge or fresh authorized assignment. Completion of affected work waits for resolution; unrelated work continues. New business choices go to the user.

Exit: overlapping edits, deletes/renames, stale bases and interrupted publication preserve both contributions. Document that protocol compliance is not filesystem access enforcement; hosts permitting unrestricted bypass cannot guarantee preservation. Depends on phase 4.

### 6. Add durable transcripts and nonblocking closure

Extract/test the conservative reader from `hai_agents_library/agents/codex-chronicle-manager/scripts/read_codex_source.py` as adapter code, preserving its identity, representation and partial-source protections. Keep selected source authority explicit; never broadly discover sessions. Journal available message events durably before acknowledging capture, then idempotently reconcile Activity-local events and derive Markdown. Store exact decoded user/assistant messages with provenance and occurrence identity; tool activity has separate linked logs. Repeated identical text remains distinct.

Keep lifecycle closure independent from capture/synchronization status. Replace `recording_gate.py` as a closure prerequisite with recording-status assessment; preserve historical evidence and any separately applicable commit/export obligations. Closed Activities accept assigned catch-up without reopening. Retain outbox/source evidence until verified materialization and explicit retention policy permits cleanup. Advance checkpoints only after durable verified writes.

Exit: close while source/sync is unavailable; restart, duplicate delivery, partial JSONL, source rotation/change, crash between journal/render/checkpoint, archive races and late final replies all retain attributable available data without duplicate rendering. Unsupported capture boundaries report gaps; no zero-loss or background-service promise. Depends on phases 1, 3 and 5.

### 7. Build and rehearse explicit environment migration

Add a preview/apply/resume migration tool and release migration guide. Inventory only affected state, configuration, packages/catalogue, configured Activity stores and transcript records. Produce mappings, hashes, preserved-byte backups, proposed changes and unresolved conflicts before applying. Record each verified step in a migration journal; ordinary startup and package extraction never upgrade.

Support explicit format-2 and format-3 paths, reusing the specification extraction rules of `migrate_specification_configuration.py` where applicable. Preserve specification and Git owner settings, chronicles enablement/threshold, profiles, unknown fields and local package differences. Map retired role-specific configuration only where semantics are lossless; preserve unmapped bytes with an archived/unmapped inventory and report them as inactive, never discard or silently reinterpret them. Missing required installed contracts or conflicting destinations stop the affected conversion; do not invent values or silently install owners. Earlier formats receive a separate explicit staged migration assessment.

Preserve Activity IDs, inputs, revision history, timestamps, original implementation markers, archived paths and exact transcript/checkpoint evidence. Legacy work stays legacy: no invented runs, host IDs or zero-token usage. New runs begin at cutover. Preserve old transcript formats/readers where needed; conversion is separately attributable. Exit: fixtures covering active/closed, custom locations, malformed inputs and partial migrations pass byte-preservation checks; rerun is a verified no-op or explicit resumable state, never duplicate conversion. Depends on phases 3–6.

### 8. Update consumers and remove obsolete core roles

Update affected golden packages under `hai_agents_library/agents/`: agent-definition-manager, business-analyst, solution-architect, software-developer, quality-assurance, specification-manager, git-manager, release-manager and codex-chronicle-manager. Replace old owner/path/permission references with runtime contracts, retain domain scope, and remove Chronicle’s exclusive ownership of automatic capture. A retained Chronicle package can provide optional diagnostics/import workflows through the generic contract.

Stage complete source packages beside the new core. Source edits do not update installed `.hai_env/agents` snapshots. Compare and explicitly replace selected installed packages, preserving customizations/settings/catalogue membership and recovery copies. Report incompatible unupdated packages before selecting them. Update release-manager’s state-contract path and package allowlist language, Git’s recording consumers, and specification test fixtures.

Only after replacement paths, consumers and migration rehearsals pass, delete `.hai/agents/leader`, `.hai/agents/environment-manager` and the framework catalogue. Update `.hai/start.md`, README, INSTALL, library index and current conventions; preserve historical release notes/manifests as evidence. Exit: no active core dependency on removed roles, no role definition in the reusable runtime, installed packages work with the source library absent. Depends on phases 4–7.

### 9. Verify release and perform controlled cutover

Run adapted existing suites: startup, specification extraction, configuration, agent tools, role migration, recording, Codex source reader and affected optional-package tests. Rewrite `test_role_migration.py` assertions of two mandatory core roles into no-core-agent/optional-collection isolation checks. Replace blocking closure expectations in `test_recording_gate.py` with nonblocking closure plus honest capture-status assertions; retain legacy-evidence coverage.

Add integration/recovery fixtures from preceding phases and one real Codex acceptance exercise. Record platform skips and unavailable telemetry/source checks accurately. Inspect an exact-commit export containing only reusable `.hai`, license and required docs: no `.hai_env`, `.hai/agents`, credentials, histories or source library. Preserve the recorded 0.2.0 candidate; prepare a new authorized manifest/version only under separate release authority.

Cut over a backed-up test workspace, then explicitly selected real environments after verification. Pause affected writers for migration; preserve queues and recovery journals. Recovery restores compatible snapshots or resumes the journal under explicit authority, never discards newer edits through automatic rollback. Exit: all required acceptance evidence, compatibility notes, recovery rehearsal and concrete candidate are reviewable; publication remains separately authorized.

| Requirement | Primary acceptance evidence |

| 5 | Phases 2, 4: coordinator/new-Activity boundaries and explicit durable promotion. |
| 6 | Phase 5: authorized direct product/specification editing and checked publication. |
| 7 | Phase 4: unavailable/partial telemetry and deduplicated totals. |
| 8 | Phase 6: nonblocking closure, separate tool logs, late catch-up and gap reporting. |
| 9 | Phase 7: explicit upgrade, preservation, crash recovery and rerun. |
| 10 | Phase 4: new-chat coordinator linkage with selected references only. |
| 11 | Phase 5: both edits retained, resolution evidence required before affected completion. |

Material risks are host delivery/source visibility, protocol bypass by unrestricted filesystem tools, cross-platform locking/durability, migration of unknown customized packages and stale source attribution. Phase 1 resolves host feasibility early; phases 5–7 prove recoverability. No unsupported host hook or telemetry API is assumed. Full Codex support must name the verified capabilities and remaining source limitations. This planning assignment ran no product tests, migration, runtime implementation, configuration changes or Activity closure.
